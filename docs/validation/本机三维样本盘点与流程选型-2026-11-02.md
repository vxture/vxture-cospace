## 3. 对流程和格式的具体安排

| 阶段 | 本批可用数据/格式 | 接入要求 |
| --- | --- | --- |
| 原始采集 | ROS1 `.bag`；ROS2 `.db3+metadata.yaml`、`.mcap+metadata.yaml`；NYU图像序列 | 保留原消息定义、字节布局、话题、frame_id、记录时间和header时间；各格式单独适配 |
| 封存/预检 | 选中小样本＋`sample.json`＋预检JSON | 明确来源与摘要、窗口、抽取及过滤规则；字段t保持原值，在明确单位和参考点前不用于去畸变 |
| 模型输入归一化 | 可从PointCloud2派生单帧PLY或数组＋元数据 | 单帧PLY只是可视检查中间结果，不能代替IMU、逐点时间和原始来源；如需NPZ，应显式保留字段映射与坐标系 |
| 空间模型候选 | 现有`spatial.npz+model.json` | 需要新增激光输入适配；不得伪装成NYU report.json或套用NYU相机坐标。单帧候选可先验证后半程，必须声明无全局配准；多帧建图再明确轨迹和变换链 |
| 双视图/对象 | 人视图PLY，智能体表面单元，以及objects.json/ontology.json | 两视图绑定同一候选和几何摘要；不从“未观测”推断“空闲”，测试语义保持待核实 |
| 发布与消费 | 固定发布、在线查询、离线包0.1/0.2、来源追溯 | 复用已验证的选择/发布/离线流程；新数据单独建立测试空间，旧NYU版本保持不变 |

当前`preview_source_config.py`仅接受`nyu_rgbd_with_existing_poses`，独立ROS1结构预检尚未接入这一工作台构建适配器。**本批完成盘点、选样和采集阶段验证，未宣称新样本已经贯通建图、双视图或发布。**

建议下一步先将S1的单帧点云接成明确的“传感器局部候选”，贯通候选→双视图→对象→固定发布→离线消费。这样可以先检验第二种来源的流程适配，不依赖新SLAM算法或Leica外参；需要多帧场景时，再扩展窗口并接入实际配准过程。

## 4. 需要保留的检查结论

1. **下载临时文件不入选。** 发现4个`.crdownload`；即使与同名bag大小相近，也未证明完整或重复，未删除、改名或用于选样。
2. **MCAP解压缺卷。** YAML声明20卷，目录实际18卷，缺`_13.mcap`和`_17.mcap`；ZIP目录中存在两卷，合计约4 GB。现有18卷索引均可打开，但不能把不完整目录作为完整采集输入。后续只补缺卷或显式选单卷，不默认重解压全部。
3. **MCAP存在时钟域差异。** `_0.mcap`中首条ZED header约1754933127秒，bag记录时间约1761656743秒；Ouster header约11548秒。可单帧检查，不能直接按数值把这些通道同步融合。ZED的`cloud_registered`仍声明相机frame，名称不证明全局配准；抽样XYZ还出现超大有限数，需专门解码与数值范围核查，不能直接并入底图。
4. **多雷达标定存在数值异常。** `os0_128_lidar.yaml`的`T_Body_OS0`旋转块det约-0.99035、正交误差约0.18170，不是可直接采用的SO(3)旋转；`T_OS1_IMU_OS0`亦异常。保持原文件，后续核对原作者坐标约定/原始标定，不自行修矩阵。首选OS1单雷达样本当前不使用这些变换。
5. **多传感器含原始厂商包。** 人体场景的`/m1600/packet`、`/ouster/lidar_packets`等不是标准PointCloud2；现阶段优先使用已有标准点云通道，厂商包解码作为独立扩展。
6. **配对不等于增量真值。** 有/无照明序列、编号1/10/11/12/13均未在统一坐标与稳定对象身份上验证，不直接用于“候选变化自动合并”验收。
