# 智能体恢复锁与代次原型验证

日期：2026-10-27。范围：J1独立Windows原型，依据[恢复日志协议](../architecture/智能体恢复独占与提交日志协议-v0.1.md)。不接入ValidityStore、R1安装或机器人会话，不写正式数据。

## 已实现的原型边界

experiments/scripts/recovery_lock_probe.py通过Win32 CreateFileW打开稳定锁文件，使用LockFileEx独占第0字节；FAIL_IMMEDIATELY加有界单调等待，超时返回busy。持有期间共享读写但不共享删除；不按PID、mtime或TTL判断放行。句柄不继承，退出由内核释放，不重建锁文件抢占。

锁文件按卷标识/文件索引与独立ownership-test.sqlite3的控制行绑定。每次打开检查实际句柄属性，拒绝目录、重解析点和多硬链接；路径祖先沿用safe_path检查。释放后被其他文件替换时，即使拿到新文件锁，也因控制记录中的身份不匹配而拒绝。

ControlProbe只含store_id/context/generation/mode/lock_identity及模拟写入计数，不是规划中v2日志表。每次模拟查询或写入都先锁文件，再读数据库校验对象代次。begin_recovery仅增加generation并持久写mode=recovering；没有结束恢复、清理、续期、恢复计划或真实空间查询。所有正常返回仍authorized=false、robot_ready=false。

## 独立执行结果

在Windows 11、Python 3.14.3上，11个独立场景通过，证据保存在[p2-recovery-lock-001](../../experiments/runs/p2-recovery-lock-001)。子进程使用基础解释器C:/Python314/python.exe并显式装配本仓库及虚拟环境site-packages，避免Windows虚拟环境启动器的PID间接层；每次握手核对实际PID等于Popen.pid，强杀仅针对自己创建的持有者。

| 场景 | 实际观察 |
|---|---|
| normal_exit | 独立竞争者busy；持有者正常退出后重新取得同一文件身份的锁 |
| killed_owner | 独立进程被强杀后，另一进程可取得原锁 |
| live_owner_and_file_replacement | 活跃持有者持续占有，mtime改为历史值也不被抢占；删除和替换被Windows拒绝 |
| path_aliases | 相对路径持有与绝对/大小写别名竞争，仍返回busy |
| old_generation | 恢复开始后，另一进程中已打开对象的查询、写入及重复开始恢复均stale_generation；新对象也因recovering拒绝查询 |
| recovery_process_exit | 恢复开始提交后强杀恢复进程；重新打开仍保留generation=2与recovering阻断 |
| competing_recoveries | 两个预先打开相同代次的真实进程竞争，一次成功、一次stale_generation，代次只增加一次 |
| replaced_lock_identity | 无持有者时注入锁文件替换，新旧对象均拒绝lock_identity_changed |
| hardlink_rejected | 实际创建硬链接后，句柄检查拒绝unsafe_lock_file |
| lost_database | 删除合成控制库后查询失败，不自动重建 |
| junction_rejected | 实际创建Windows目录联接，路径检查拒绝；仅移除测试联接，目标库保持不变 |

pytest新增14项实例：上述11项，另加缺失目录/错误context/重复bootstrap、同进程独立句柄争用与非法超时、代次上限不回绕。独立进程场景与pytest共享同一实现，不把两次执行重复计为不同覆盖。

全量本地回归192通过、6跳过、22个子用例通过，耗时117.87秒，新增14项均通过。跳过项没有本次验收证据，不视为PostgreSQL或目标设备路径通过。

原型报告包含实际PID、文件身份、结果及三份源码摘要；见[report.json](../../experiments/runs/p2-recovery-lock-001/report.json)、[pytest日志](../../experiments/runs/p2-recovery-lock-001/tests.log)及[JUnit](../../experiments/runs/p2-recovery-lock-001/tests.xml)。故障注入中保留的锁、控制库均为小型合成资料，不含授权密钥。

## 复跑与限制

```powershell
.venv/Scripts/python.exe -m pytest tests/test_recovery_lock.py -q --tb=short
.venv/Scripts/python.exe -m experiments.scripts.check_recovery_lock --root experiments/runs/p2-recovery-lock-002
```

独立证据命令要求新目录，存在则拒绝，避免覆盖历史。测试会在自己创建的合成目录内做强杀、锁替换、数据库删除、硬链接与目录联接注入；不应指向产品数据目录。单次锁等待限制0至5秒，无自动超时接管。

JL-01与JL-02有本机独立原型证据；JL-03验证了当前本地文件系统的别名、硬链接、目录联接和文件身份检查，仍不覆盖恶意路径替换竞态、网络共享或所有重解析点类型。JL-04仅验证begin和模拟对象代次，resume、实际旧会话和完整恢复仍待J3/J4。初次测试的跨盘相对路径构造问题已改为以测试目录父路径作为子进程工作目录，修正后重跑。

本批不验证物理断电、网络文件系统、恶意磁盘回滚、管理员修改控制库、持锁线程单独退出但进程仍存活等情形；不要把内核释放文件句柄提升为设备可恢复性证明。下一批J2实现新实验库message/intent/receipt的准备与原子应用，复用锁前仍须组合验证。
