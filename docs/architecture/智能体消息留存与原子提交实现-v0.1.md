# 智能体消息留存与原子提交实现

日期：2026-10-27。状态：J2合成Windows实验实现，位于experiments/scripts/recovery_journal.py。依据[恢复日志协议](智能体恢复独占与提交日志协议-v0.1.md)。没有恢复解除、旧库迁移或真实机器人授权。

J3补充：独立RecoveryStore已实现[实验恢复状态机](智能体恢复状态机实现-v0.1.md)，使用新建user_version=3实验库；本J2默认库保持version=2，下面的J2接口限制及历史证据不因此改变。

## 存储与接收接口

JournalStore显式bootstrap只接受不存在的新目录，创建journal.lock与journal-test.sqlite3；常规打开使用mode=rw，不创建缺失库。application_id和user_version=2区分本实验格式；它不读取旧validity-test.sqlite3或J1 ownership-test.sqlite3。信任、Policy及限额共同构成固定context摘要，配置变化拒绝打开。

调用accept(binding, token, kind, intent_id=...)时必须给规范小写UUID意图ID。原字节ASCII JWS按摘要保存在messages，同事务写不可变intents。准备阶段不修改空间状态，也不返回应用成功。之后应用事务在同一SQLite连接中写states、control状态摘要/修订号和唯一receipts，提交后才返回凭据。

所有公开操作持同一个J1 StableLock，覆盖准备与应用的两个事务间隙；取得锁后核对store/context/generation及锁文件身份。新接收发现任何没有最终凭据的intent即返回recovery_required，不允许后续消息越过未确认撤回。已有intent的相同消息可读取已提交结果；未决intent不能通过重试自动执行。相同ID换消息拒绝intent_conflict。

## 状态与凭据

复用既有测试验签、受限委托和时间规则；J2独立实现状态应用，不调用v1文件pending写入。状态仍包含完整binding、内容/状态/grant证明和累计终止撤回。epoch、序号高水位、同序冲突、grant状态摘要/策略绑定、终止撤回及过期判定继续生效。

| 结果 | 状态及凭据 |
|---|---|
| applied | 实际改变状态，state_revision加1；凭据绑定前后版本及状态摘要 |
| idempotent | 同状态消息，版本与状态摘要不变；不刷新离线期限 |
| rejected | 确定性状态规则拒绝，保留原消息及拒绝原因，前后版本/摘要不变 |
| 无最终凭据 | 准备后中断或未知故障；保留未决，查询和后续接收拒绝 |

签名、角色、scope或签发时间预检失败不创建intent。准备之后再次验签失败或非白名单故障不记为可忽略的逻辑拒绝，保持未决；SQL/OSError在当前对象额外锁存storage_error。未知签名问题不能通过写一个rejected凭据绕过。

messages、intents、receipts有禁止UPDATE/DELETE的触发器及外键约束。它们保留历史，即使最新状态已被替换仍可按ID导出原消息和凭据。触发器是本地工程约束，不是对管理员篡改的密码防护；当前没有全历史重放审计、日志裁剪或坏库修复。

receipt(intent_id)在锁内查询已提交凭据；export_intent提供契约格式的原消息留存记录。两者仅诊断，不能当成有效能力。凭据符合[交换Schema](../../contracts/schemas/recovery-journal-v0.1.md)，真实摘要/版本关系由事务和测试验证，不能通过导入JSON制造成功记录。

## 状态摘要与限额

状态摘要绑定store_id、context、state_revision及按identity排序的全状态；每项含完整binding、三类原消息摘要、最高epoch/sequence与排序去重的撤回集合。打开和每次操作验证当前状态摘要；每个当前证明还必须匹配messages中的原字节及关联身份。摘要用于发现内部不一致，不提供外部硬件防回滚。

首版默认最多128个不同消息、256个意图、2MiB消息原字节总量、64个状态。配置结构限定上界分别为1000、2000、32MiB和200，消息仍受现有MAX_TOKEN约束。超过任一配额在准备前拒绝，不丢弃历史；修订号达到2^53−1拒绝继续增长。限额是实验工程参数，不是机器人产品性能指标。

## 查询与故障边界

decide持OS锁，先核对控制状态、未决集合和当前状态摘要，然后复用合成门禁的验签及时间交集。现有门禁判定内部单独打开读取连接；OS锁覆盖整个判定，所有J2合规写入均被串行化。没有把真实FilePackages会话自动换成J2；公开返回仍authorized=false、robot_ready=false。

| 中断点 | 重新打开后的结果 |
|---|---|
| 准备提交前 | 消息与意图事务回滚，原合成有效状态可继续判定；未承诺接收 |
| 准备提交后 | 原消息与intent保留，没有receipt，查询recovery_required |
| 状态写入后、receipt之前 | 应用事务整体回滚，intent未决 |
| receipt插入后、提交前 | 状态、控制版本及receipt一起回滚，intent未决 |
| 应用提交后、响应前 | 状态与唯一receipt均已提交，按原ID查回结果，不再次应用 |

本批用注入SQLite异常、实际约束失败及独立子进程os._exit验证；不是物理断电、进程外强杀、存储设备持久性或Windows缓存验收。文件系统完全不可写、准备前即失败，仍无法保证跨进程留痕。缺库不重建，当前状态不一致不放行，但整套数据库恶意回滚未防护。

验证记录见[消息留存与原子提交验证](../validation/智能体消息留存与原子提交验证-2026-10-27.md)。下一步J3实现受控begin/resume、恢复计划CAS与对账提交；J2中的generation/mode仅为预留控制和拒绝条件，没有公开恢复操作。
