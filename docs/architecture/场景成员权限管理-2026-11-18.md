# 场景成员权限管理

组织订阅、应用授权和场景操作角色分别生效。产品默认尽量共享可见性：通过平台使用授权的同一工作区成员，均可查看、预览和查询该工作区显式绑定的全部场景；资料管理、构建、导出、关联、发布和管理操作继续按场景角色分配。“我的场景”不按创建者筛选，不因缺少单独授权而对正常成员返回空目录。

## 使用流程

1. 普通成员进入“我的场景”即可看到本工作区全部场景，无须申请查看权限。需要额外操作权限时，在“场景权限”中申请协作权限。
2. 工作区所有者或对应场景管理者打开同一入口，选择成员、场景和角色，填写原因并保存；可对不同场景分配不同角色，选择“默认查看者”撤销额外操作权限，保留基础查看权限。
3. 成员刷新页面后使用获授角色。服务端每次业务请求重新读取策略；撤销工程师或管理者后，原有写入、构建、导出和发布入口失效，场景仍可查看。跨工作区访问始终拒绝；平台应用授权撤销后，也无法继续查看。

查看者（viewer）可预览、查询和读取服务对象；工程师（engineer）拥有全部场景操作权限，包括新建场景、资料管理、构建、导出、关联、位置与场景配置、服务对象管理及发布；不具备人员角色管理权限。管理者（manager）拥有工程师全部权限，增加当前工作区系统高级配置（当前已实现的工作区本体规则配置）和所管理场景的人员角色授权。拥有当前工作区任一场景工程师/管理者角色可新建场景；工程师新建场景仍为工程师，不升级为管理者。所有者管理本工作区全部场景的成员授权；管理者只调整自己所管理场景的授权，不能借此修改其他场景。高级配置限于当前工作区，不开放全局配置、基础设施或平台订阅管理。

所有者保留平台规定的、限于当前工作区显式绑定场景的管理基线。修改单独场景授权不能降低这一基线；所有者变更须在平台完成。

## 身份来源与接口

已核对平台 Console：`GET /api/iam/workspaces/:workspaceId/product-seats` 返回按产品分组的 holders（userId/userNo/displayName/grantedAt），需 Console 会话和 workspace.member.manage。平台 API 的 `GET /platform/product-access` 仅查询 OBO 当前用户是否获权，没有批量名单。应由平台增加绑定当前组织、工作区、调用产品的只读授权人员接口；CoSpace 不转发 Console cookie 或直接访问平台数据库。本次没有读取线上实际名单。接入批量接口前，当前实现使用以下临时候选流程。成员显式申请时，从服务端已验证的身份保存 issuer、org_id、workspace_id、subject 和显示名；不接受浏览器声明这些信息。所有者或管理者可以选择本工作区的申请成员，以及已有本工作区场景授权的成员。此列表是产品授权候选集合，不是组织全体成员目录或商业席位账本。新同事无需申请即可查看场景；首次分配额外操作角色前需先申请协作。不支持手填任意用户 ID 授权。

| 接口 | 权限及行为 |
| --- | --- |
| `GET /api/scene-permissions` | 普通成员只读本人申请状态；所有者读取当前工作区的候选成员、场景、授权和最近 50 条操作记录；管理者只读其管理场景的授权和操作记录 |
| `POST /api/scene-permissions/requests` | 空 JSON，登记本人协作申请；重复提交不重复新增，不授予额外操作角色 |
| `POST /api/scene-permissions/grants` | 所有者或对应场景管理者提交 `expected_revision`、`subject`、`space_id`、`role` 和非空 `reason`；role 为 viewer/engineer/manager，null 表示移除单独授权、回到默认查看者 |

三个接口均经过原有会话、平台订阅和应用授权门禁；写入继续使用 Origin 和 CSRF 校验。请求参数不能替换当前组织或工作区。

## 持久化与并发

复用现有 `space-policy.sqlite3`，不变更保存的 `SpaceAccessPolicy` 格式。产品组装 `serve_platform_workbench.assemble` 显式启用 `workspace_scene_visibility=True`；请求通过会话及平台门禁后，读取策略时使用 `WorkspaceSceneAccessPolicy` 提供限于精确 issuer/org/workspace 绑定的查看者基线。显式角色继续生效，不自动写入个人 grants。底层独立工程组装默认保留原显式授权模型；S2S 消费端不继承人类成员的查看基线。申请记录按 issuer/org/workspace/subject 唯一保存；只读请求不创建数据表。

授权写入在 `BEGIN IMMEDIATE` 中重新读取策略、检查场景归属和期望修订，保留其他场景及工作区的授权。策略、原策略历史和新增的场景权限操作记录在同一事务提交；记录失败则全部回滚。冲突返回 409，界面要求重新读取后核对，不自动重放写入；相同角色的无变化提交不新增修订或审计。记录包含操作人、目标成员、场景、前后角色、原因和时间。

## 验证与发布边界

新增 HTTP 与服务测试覆盖无申请/无单独授权的成员可查看全部本工作区场景、额外角色变更及撤销后保留查看、原显式授权工程模式、仅所有者管理、CSRF、伪造身份、跨 issuer/组织/工作区隔离、旧修订冲突、并发仅一方成功和审计失败回滚。浏览器验收使用独立本地模拟身份及空场景运行根，不证明生产账户已经获权。

生产生效仍须通过 PR、必需检查、release tag 构建镜像和 production Environment 审核；本地实现及验证不等于已经部署。

## Header 组织上下文与平台依赖

Header 使用已验证身份中的组织简称和真实工作区名称；面板展示组织全称、Logo、组织类型和工作区。缺少简称时保留全称，缺少名称时明确提示待补全，不从组织 ID 推测简称或把工作区统一写成 default。应用中心跳转 https://ruyin.work/，组织信息跳转 https://console.vxture.com/，两项最小高度 48px。

平台现有签名字段为 active_org_name、active_org_type、active_workspace_name；CoSpace 已兼容可选 active_org_display_name 和 active_org_logo_url，均只用于展示，不参与授权。历史会话在有效签名令牌上更新展示投影。简称和产品可用 Logo 的平台交付跟踪 [#638](https://github.com/vxture-platform/vxture-platform/issues/638#issuecomment-6980860463)。授权人员名单接口跟踪 [#706](https://github.com/vxture-platform/vxture-platform/issues/706)，交付前仍采用上述已验证成员申请流程。本次没有读取真实授权名单，也未部署生产。
