# 故障恢复与受控重试设计

日期：2026-10-26。状态：I4设计草案，I4a独立原型已开始验证；产品恢复尚未实现或通过故障验收。依据：[任务设计](受控导入与构建任务设计-v0.1.md)、[实施清单](受控导入与构建任务实施清单-v0.1.md)。

## 1 范围与结论

首批恢复只支持受信任的单机、本地文件系统、单个固定检查子进程和PostgreSQL。恢复由内部交付工程师通过本机CLI明确发起，不按心跳过期或任务运行时间自动接管。恢复不形成空间候选、真值或服务发布，不修改当前服务指针。

恢复必须同时解决两件事：证明旧监督进程和子进程已经结束；使旧执行永久失去提交资格。仅有数据库状态、PID、超时或锁文件存在与否均不足以证明安全。无法取得证据时返回阻塞原因，保留原状态。

失败重试使用同一job的新attempt，保留原规格、输入、配置和环境指纹。改变任一项或对成功任务主动重算，应提交新job并记录replay_of；不改写旧job规格。

## 2 当前实现差距

当前0003迁移对attempt.job_id设置唯一约束；claim只返回attempt_id；finish只检查running状态。运行器没有持久化进程启动身份，也没有覆盖启动空窗的互斥协议。报告读取依赖唯一attempt。上述条件必须一起调整，不能先开放retry按钮。

当前封存后数据库失败会留下running任务和不可见孤立产物。这是已知失败状态，不得根据文件存在推断成功。此前66个测试及22个子用例不构成本设计的恢复证据。

## 3 模型与事务约束

| 实体 | 拟增字段或约束 | 用途 |
|---|---|---|
| job | active_attempt_id、successful_attempt_id、fence（单调整数）、replay_of（可空） | 指定当前执行、唯一成功报告及执行代次 |
| attempt | attempt_no、fence、owner_session、process_record、interrupted原因 | 保存每次执行及进程证据 |
| attempt约束 | UNIQUE(job_id, attempt_no)，替代job_id唯一约束 | 支持同一任务的连续尝试 |
| event | event_seq、actor、reason、attempt_id、前后revision、fence、evidence摘要 | 按job顺序追加状态变更与恢复依据 |

attempt_no从1开始，在job行锁下分配；中断或失败的attempt不复用。fence在认领和恢复撤销执行权时递增，从不回退。job引用的attempt必须属于该job；通过复合外键或等价数据库约束保障。successful_attempt_id只指向已成功且产物绑定通过的attempt。

所有写入遵循“本机job互斥锁 → job行锁 → attempt更新”的顺序；数据库只在短事务内持锁，不等待进程退出。只读详情继续在job行锁下取得一致状态。事件与业务变更在同一事务提交；旧事件保留，不补造缺失的历史actor。

finish同时匹配job_id、active_attempt_id、fence、owner_session、expected_revision及running状态，再更新attempt、job、成功引用和事件。任一不符则整笔回滚并返回stale_execution或state_conflict。产物内的context和artifact清单也绑定同一fence、attempt、规格及输入摘要。数据库提交成功前，产物不能经报告接口消费。

## 4 进程所有权与启动空窗

### 4.1 互斥与身份

infrastructure提供Windows本机内核互斥对象，名称由规范化data-root、数据库实例标识和job_id派生；限制在同一受信任执行账户下使用。互斥对象由监督进程在claim前取得，覆盖启动、监督、产物封存和finish提交，进程退出后由操作系统释放。放弃的互斥对象只表示需要检查，不能直接判定任务可恢复。普通磁盘锁文件只用于诊断。

启动前持久化监督身份：host_id、boot_id、owner_session、PID、操作系统进程创建时间及协议版本。子进程同样记录PID和创建时间。PID相同但创建时间不同视为其他进程；权限不足、身份缺失或主机不匹配均为unknown，禁止凭猜测杀进程或恢复。

### 4.2 子进程启动协议

首批Windows适配修订为“创建Job Object → 通过PROC_THREAD_ATTRIBUTE_JOB_LIST原子关联并挂起创建子进程 → 登记身份 → 恢复线程”。Job Object配置KILL_ON_JOB_CLOSE，监督进程持有唯一不可继承控制句柄，子进程及其句柄不能延续所有权。固定worker不允许启动后代进程。原型使用active_process_limit=1验证此限制。实际worker已通过基础Python加显式venv启动绑定完成本机试验，见[环境记录](../validation/检查worker环境绑定验证-2026-10-26.md)；运行器集成仍待实现。

不再采用“先创建再加入”的协议：其间父进程死亡可能留下挂起进程。原子关联要求操作系统支持扩展启动属性；创建失败直接返回错误，不回退到普通Popen。创建返回后、身份登记前强杀监督进程，原型已观察到子进程退出；创建前强杀未创建子进程。该结果只覆盖本机已验证环境，不能推导所有Windows版本均支持。原型期间CIM进程清单查询被拒绝，因此不将全机枚举作为启动窗口安全性的必要补救。

正常登记后，worker仍需在工作目录原子写入启动确认，再等待监督进程的执行许可；许可绑定attempt/fence/session。监督进程只有在身份已持久化且数据库仍确认当前执行权后才发送许可。原子关联、Job Object句柄隔离和实际worker环境未验证前，不开放恢复；不能退化成普通Popen加PID检查并声称等价安全。原型许可只用于控制试验阶段，未实现数据库执行权或fence校验。

旧监督进程若还活着会继续持有互斥对象，恢复请求返回owner_alive，不撤销其资格。监督进程退出后，恢复器在锁内确认已登记子进程结束，并检查启动空窗；任何存活或unknown均不转换状态。启动许可与执行代次检查不能替代操作系统进程隔离。

## 5 状态与操作契约

| 操作 | 前置条件 | 原子结果 |
|---|---|---|
| run | queued、revision匹配、取得job互斥锁 | fence递增，新增running attempt，绑定active_attempt，job→running |
| finish | 当前attempt/fence/session/revision均匹配 | attempt及job→succeeded/failed，清空active引用；成功时登记successful引用 |
| recover | running、revision匹配、独占job锁、旧监督及worker确定结束 | 旧attempt及job→interrupted，fence递增、清空active引用，保存证据及事件 |
| retry | failed/interrupted、revision匹配、无活动执行、固定输入及环境仍可用 | job→queued，追加retry_requested事件，暂不创建attempt |
| cancel | queued、revision匹配 | job→cancelled，不新增attempt |

每个成功变更revision递增一次。恢复不是取消运行中的任务；running取消仍不支持。succeeded和cancelled不允许retry。重复提交同一旧revision返回冲突，调用方重新查询，不悄悄执行第二次重试。

拟定CLI为 `recover JOB --revision N --actor X --reason TEXT`、`retry JOB --revision N --actor X --reason TEXT`。先提供只读恢复检查，输出recoverable、owner_alive、worker_alive、identity_unknown、host_mismatch或legacy_unverifiable及证据摘要；正式recover必须在锁内重新检查，不能直接信任前一次检查结果。

recover不主动终止身份不明的进程。对确认为本次attempt的遗留挂起worker，后续实现可提供显式终止步骤，必须核对创建身份并等待退出后再次检查；不能把发送终止信号等同于已退出。数据库不可用时不执行状态转换或开放新执行。

## 6 文件、重试与报告

运行目录仍按job/attempt隔离；封存目录不可覆盖。旧attempt即使留下完整artifact，也不能在新attempt中复用身份。封存后数据库失败：保存目录和诊断证据，确认执行结束后将旧attempt标记interrupted，再由新attempt完整执行。首版不提供孤立产物直接补登记成功或自动垃圾回收。

retry在排队前检查固定dataset可读、摘要不变、原环境指纹仍匹配；run再次检查以防排队期间发生变化。输入损坏保持失败状态并返回input_unavailable；环境改变需新建job。新job的replay_of只表达来源，不继承原成功结论。

报告由successful_attempt_id定位，校验job、attempt、fence、输入及规格摘要；禁止选择数组第一个或“最新目录”。详情按attempt_no返回全部历史，并显示恢复原因和证据摘要。失败或中断的attempt只显示诊断，完整孤立报告也不能显示为成功。

## 7 迁移与兼容

拟增0004迁移，实际文件在实现阶段创建。先停所有旧CLI/worker并备份数据库和数据根目录；旧程序不能与新恢复协议同时写库。

旧attempt回填attempt_no=1；成功job绑定原成功attempt，验证其原格式产物时使用明确的legacy格式分支。旧运行任务缺少进程证据，标记为legacy_unverifiable，不伪造host、boot或session。不能自动把旧running任务改成interrupted；需要单独的停机盘点流程及可核验证据，首批在线恢复拒绝处理。

job读取契约拟升为0.2，增加interrupted、attempt序号及引用字段；Schema、API、CLI、JobManager.report、JobReader和工作台同步升级，明确拒绝不兼容客户端。旧只读列表不应因未知状态展示成功。升级测试覆盖0003已有成功、失败、排队、运行记录；降级涉及多attempt数据，不承诺无损，采用备份恢复。

## 8 分批实施与出口

1. I4a：先完成Windows进程所有权适配和真实启动空窗强杀试验；无法证明安全则记录阻塞点，不开放recover/retry。独立原型已完成7项首批试验，实际worker环境新增7项试验通过；重启、身份/权限分支及运行器集成仍待验证，见[进程记录](../validation/Windows进程所有权原型验证-2026-10-26.md)和[环境记录](../validation/检查worker环境绑定验证-2026-10-26.md)。
2. I4b：实现0004、执行代次CAS、状态/事件/契约升级，验证旧执行提交被拒绝及并发单一胜者。
3. I4c：提供本机恢复检查、recover/retry、历史报告读取与工作台只读展示，完成端到端故障验收。
4. I4d：另行设计导入恢复。导入的validating状态、封存后数据库失败、同键重入及来源消失不能套用job进程协议；此前IN-06仍未闭环。先保持dataset不可见，保留孤立目录，不自动采用或清理。

各批按[故障验收清单](故障恢复与受控重试验收清单-v0.1.md)留存证据。I4a–I4c通过只说明本机合成检查任务恢复有效；完整I4还需导入恢复。P1算法可行性、P3真实构建和生产恢复继续独立验收。
