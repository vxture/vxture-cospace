## 1 目标和存储边界

要解决的是：为每个已持久接收的证明保留原字节，区分待处理、已应用、幂等和明确拒绝，并让恢复决定与状态变更原子提交。恢复完成仅表示本地状态已对账；是否可使用仍取决于签名、撤回、时间和会话门禁。

规划独立的实验ledger-v2目录和数据库，不原位改写旧validity-test.sqlite3。旧库没有完整历史，不能从最新状态反推历史撤回；旧pending只能继续核对，不能靠导入新库解除。旧设备的受控迁移、信任变更及丢库恢复另立协议。

v2以单个SQLite事务日志为权威，本地消息、意图、提交凭据、累积撤回、恢复控制状态均在同一数据库。外部JSON只是诊断导出，不参与清除或放行判断。此设计避免把“删除文件”与“提交恢复决定”组成不可原子的两步。J2已实现其中消息/意图/提交凭据及当前状态，恢复控制操作尚未实现；没有迁移，现有v1仍由pending文件阻断。

## 2 全体参与者的独占协议

首个参考实现采用单个稳定锁文件的操作系统独占锁，串行保护本地accept、decide、受控bootstrap和recovery。查询只在读取及作出门禁判定期间持锁，不涵盖网络响应或机器人动作。优先验证小型包的正确性，暂不承诺高并发性能；共享读锁属于后续优化。

锁文件不能通过删除/重建抢占，PID、文件mtime和租约超时都不是所有权凭据。进程退出后由内核释放锁；存活但无响应时返回busy，不自动强杀或偷锁。Windows独立原型已采用LockFileEx的同一字节区间，其他平台需独立适配和实测。实际跨进程行为已有J1本机证据，但与v2门禁及日志的组合仍待实现验证。

顺序固定为OS锁→校验存储身份和代次→SQLite事务，禁止先持数据库写锁再等待OS锁。所有参与者必须遵守；旧程序不识别v2目录，禁止混用。只读诊断可以不持锁，但结果只算观察，不得产生恢复决定。一致性导出必须在维护锁下使用SQLite备份协议，不能简单拷贝活跃主库。

数据库保存随机store_id、固定context_sha256、generation、state_revision和mode。对象打开时记住store_id/context/generation，每次decide或写入在锁内重新核对；失配返回stale_generation，不自动刷新旧会话。generation仅由受控恢复开始递增，不能用消息自带字段提升。锁本身不防管理员替换锁文件或恶意回滚磁盘，当前限定本机受信目录。

## 3 持久记录及规范摘要

结构规范见[日志交换契约](../../contracts/schemas/recovery-journal-v0.1.md)。日志不是新的远程授权凭据；本地receipt即便结构正确也不能替代消息签名。

| 记录 | 最小职责 |
|---|---|
| store_control | store_id、上下文摘要、代次、mode、state_revision；初始化身份不复用 |
| messages | 以token_sha256保存原始ASCII JWS字节、kind、identity与binding_sha256；不可覆盖 |
| intents | intent_id、消息引用、接收代次、准备时状态版本；不可改换消息 |
| receipts | 每个intent唯一最终结果，包含前后版本/状态摘要、结果与原因 |
| states | 当前证明引用、完整binding、高水位和累计终止撤回，仍遵守R2原有规则 |
| recovery_runs | recovery_id、当前代次、计划摘要、进度和最终结果；保留中断记录 |

messages与intents准备阶段同事务落库；receipts与对应states变更同事务落库。每个intent最多一个最终receipt，禁止单独补写“看起来成功”的凭据。receipt、message、intent及恢复证据首版不做自动垃圾回收。达到字节/行数配额时拒绝新接收，不能截断历史后继续运行。

token_sha256是原始JWS ASCII字节的SHA-256；binding_sha256是现有canonical(binding)摘要。identity仍为canonical([deployment,scene_id,package_sha256])摘要。状态摘要使用canonical序列化的规范对象：store_id、context_sha256、state_revision，以及按identity排序的全部状态；每项含完整binding、内容/状态/grant的token摘要或null、最高epoch/sequence及排序去重的累计撤回集合。摘要不包括墙钟、OS锁、generation或receipt行，避免自引用；这些字段在比较条件中单独绑定。

规范对象使用当前canonical的UTF-8、排序键与紧凑分隔形式；数组顺序按上述定义，不允许浮点、重复身份、重复撤回、额外字段或隐式默认值。跨语言标准化尚未验收，首版仅Python实验。结构校验不核验摘要真实性。

## 4 正常接收：准备与应用分开

1. 有界解析及签名预检后取得OS锁，重新确认store_id、上下文、对象generation、mode=normal。任何尚无receipt的intent存在时拒绝新的接收，要求显式恢复；不让后续状态越过未确认撤回。
2. 准备事务：保存不可变原始消息及intent，记录prepared_revision后提交。此时只表示已持久接收，不返回应用成功。相同intent_id+相同原字节可查结果；同ID不同原字节拒绝。不同ID的相同消息仍按状态规则处理，不能刷新有效期。
3. 应用事务：重新核对上下文和版本，完整验证证明与状态约束，原子写states和receipt。改变状态才递增state_revision；幂等或明确逻辑拒绝不递增，前后状态摘要必须相同。已签时间不因准备、应用或恢复而更新。
4. 提交成功才返回receipt引用。响应丢失时通过相同intent_id读取结果，不重做状态变更。SQLite错误使本对象锁存故障；已准备但未最终处理的intent使新对象也拒绝查询。

准备事务之前就失败的输入没有“已持久接收”承诺；整个存储不可写时不能保证跨进程留痕。准备提交结果不确定时必须重新读库核对，不能仅根据异常判定未提交，也不能先返回成功。库丢失、损坏或控制记录缺失拒绝打开，不自动bootstrap。恶意删除整套存储与物理断电持久性仍需独立防护/实测。

## 5 恢复状态机及比较条件

| 持久阶段 | 行为 | 中断后 |
|---|---|---|
| normal | 有未决intent也拒绝查询；无未决时仍逐次执行完整门禁 | 不自动处理未决项 |
| blocked | 受控begin-recovery持OS锁，同事务递增generation并记录recovery_id；所有消费拒绝 | 下次恢复在锁内继续，旧对象已失效 |
| planned | 读取完整消息与提交日志，验签、重放/对账并封存计划摘要 | 对比store/context/generation/版本和未决集合，失配拒绝 |
| reconciled | 在单事务内应用全部可解决项、写receipt及恢复结果，核验目标摘要后转normal | 若响应丢失，读取同recovery_id结果；不能再次应用 |

blocked/planned均为mode=recovering，不允许普通接收或查询；阶段变化本身不表示空间能力获准。计划存在retain_blocked项、未知消息、历史不完整或验签失败时不可转normal。任何恢复失败保留原证据；不生成“部分成功后已恢复”的结论。

每个恢复计划绑定store_id、固定context_sha256、当前generation、recovery_id、expected_state_revision、before_state_sha256、完整未决集合摘要、每项原字节摘要与拟处理结果，以及target_state_sha256。未决集合按intent_id排序，项目只含intent_id、message_kind、identity、token_sha256；不依赖文件名或时钟。生成计划和提交决定都必须在OS锁下；跨调用释放锁时，恢复mode仍持久阻断，下一次操作重新比较全部条件。

中断后可由显式resume-recovery在锁内认领同一个recovery_id并递增generation，旧计划因代次失配不可执行；重新对账生成新计划。已完成recovery_id只允许读结果。开始另一个恢复不能重置未完成任务；代次是防旧对象继续写入的比较值，不是可脱离OS锁的分布式租约。J3进一步规定完成时再推进一次代次，让恢复期间新开的对象也失效；receipt/result保留处理时的代次，control进入下一代次。

最终提交事务同时核对计划摘要及全部比较条件，将每个未决项落为applied、idempotent或rejected，保留全部原始消息与原因；任何一步失败则整体回滚，mode保持recovering。receipt中的代次是实际处理代次，可高于intent准备代次，但store/context/intent/token绑定不得变化。之后旧对象仍stale_generation，新对象必须重新取得有效时间锚并开新会话；J3只验证注入测试时间，真实时间锚与会话装配仍待实施。

## 6 对账规则与撤回约束

有匹配receipt且前后状态链及不可变消息可验证时，认定该intent已最终处理；当前states没有该证明并不否定历史提交。没有receipt时，只有在v2原子事务及完整日志假设成立、控制记录与状态摘要一致的情况下，才能判为“准备后尚未最终处理”。来自v1、备份不完整或任意手工补录的数据不能使用这一推论。

恢复重放必须重新验证原字节签名、受控测试委托、完整binding和角色范围。历史证明的签发时点可验证性与当前使用有效期分开：历史到期不抹除已发生的撤回，也不为过期grant续期。无法确认历史签名或撤回来源时保持blocked，不能简单记rejected后跳过。

apply仍服从epoch授权、序号高水位、终止撤回累计和grant绑定；不能以恢复为由清零撤回、降低版本或把restricted改allowed。仅确定性逻辑拒绝且能证明不丢弃历史撤回时可record_rejection，必须给稳定原因；证据不足用retain_blocked。缺失新的有效grant时，日志可对账完成，但查询仍grant_missing或expired。

## 7 实施拆分与出口

1. J1：独立OS锁及代次原型，验证两个真实进程竞争、持有者退出、存活者超时、旧对象拒绝和路径限制。暂不接R1或迁移v1。
2. J2：新实验库的message/intent/receipt原子路径，故障屏障覆盖prepare、apply与响应丢失，验证完整历史及配额。
3. J3：恢复计划、CAS提交、resume、撤回对账及全量回归；仅合成，不自动释放真实设备。
4. J4：组合门禁、只读审计和兼容入口；迁移与正式时间来源另设验收，不因此完成R2c/R2d。

验收场景见[实施与故障清单](智能体恢复日志实施与验收清单-v0.1.md)。协议初稿只确认设计及交换结构，后续J1补充独立锁原型；运行恢复及断电仍无证据，独立测试结果不提升为完整v2协议验收。
