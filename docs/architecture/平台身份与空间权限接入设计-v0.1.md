# 平台身份与空间权限接入设计 v0.1

日期：2026-11-03。本文将 CoSpace 接入 yucer 所使用的 Vxture 平台认证约定，作为后续真实 HTTP 接入的边界。当前已完成 I1：服务端验签适配器、平台工作区到物理空间的显式绑定、产品角色与权限规则及负向测试。RP 登录回调、中心会话查询和所有 HTTP 路由门禁尚未在本批宣称完成。

## 1. 复用平台认证，不建立第二套账号

认证权威是 `accounts.vxture.com`。设计参考 yucer 的 `portals/app/app/auth/lib/claims.ts`、`auth/lib/login-state.ts`、`auth/logout/route.ts` 及平台的 `docs/30-design/identity/080-rp-integration.md`。平台使用 OIDC Authorization Code + PKCE；CoSpace 将注册自己的 `client_id`、secret、回调地址和登出地址，不能复用 yucer 的 cookie、Redis session 或客户端密钥。

浏览器只保存 CoSpace 域的 host-only HttpOnly 会话 Cookie。CoSpace 服务端保存令牌并验证 RS256、固定 issuer、audience、exp、iat、sub 和 kid；JWKS 只从服务端配置的可信地址读取，禁止使用 token 中的 `jku`、`jwk`、`x5u`。平台账号的空闲和总时限不由 CoSpace 定义，登录状态查询与全局登出沿用 accounts 规则。

平台 access token 必须携带：`sub=usr_...`、`userType=tenant_user`、`account_status=active`、`active_org`、`active_workspace` 和 scope 前缀的 `roles[]`。角色值域是 `owner/manager/member/readonly/guest`；裸 `owner`、`admin` 不产生治理权限。`workspace:owner` 只表示当前平台工作区的产品管理员基线，不能跨工作区或绕过 CoSpace 的空间绑定。

## 2. 两层作用域

平台组织和工作区是身份上下文；CoSpace 的物理空间是业务资源。二者必须用持久化绑定表达：

| 层 | 标识 | 用途 |
| --- | --- | --- |
| 平台 | `issuer`, `active_org`, `active_workspace` | 认证上下文和租户边界 |
| CoSpace | `space_id`, `project_id` | 真值、候选、发布、离线包的物理资源边界 |
| CoSpace 成员授权 | `(issuer, sub, space_id, role)` | viewer / engineer / manager 产品权限 |

空间目录没有绑定记录时，不因名称、项目、历史发布或 token 的 owner 角色推断归属。旧的本机工程数据也不会自动迁移到当前工作区。`workspace:owner` 仅在已明确绑定到其 issuer / active_org / active_workspace 的空间上提供产品管理员基线。代码不在请求期间创建或改写成员授权。将平台 owner 本地设为 viewer 不会降低平台的 owner 基线；要取消该基线须调整平台角色，普通产品成员的权限仍由 CoSpace 授权记录控制。

## 3. 产品能力

| 产品角色 | 能力 |
| --- | --- |
| viewer | 空间预览、空间查询 |
| engineer | viewer + 导出、资料管理、构建、空间关联编辑 |
| manager | 全部能力：发布、空间管理 |

能力枚举固定为 `space.preview`、`space.query`、`space.export`、`data.manage`、`build.run`、`association.edit`、`publication.manage`、`space.manage`。治理角色、产品角色和商业权益三轴分离；本产品当前不引入计量或订阅门禁。

服务端每次请求按以下顺序处理：读取 CoSpace RP 会话 → 验证 access token / 中央会话状态 → 得到 `(issuer, sub, active_org, active_workspace)` → 查空间绑定与成员授权 → 再读取保存的空间、候选、发布或输入记录。授权失败先于资源读取，避免通过 404/响应差异泄露未授权空间是否存在。所有 artifact 记录必须重新核对 `id`、`space_id`、`project_id`，不接受请求体声明覆盖保存归属。

## 4. 与 yucer / accounts 的会话边界

后续 I2 实现一个 RP 会话和一个 `LoginAuthority` 适配器。所有业务板块共享同一会话，并用服务端存储的跨进程锁合并查询和单次 refresh token 更新。页面访问、预取和后台探针不能各自续期。中心 `POST /oidc/session/status` 接口使用平台规定的 Basic client credentials 与严格 JSON：`{"sid":"...","active":true}`，返回 `{"valid":true,"next_check_at":...}` 或 `{"valid":false}`；预取、轮询等不报告 active。网络错误、5xx、invalid_client 不转换成 `valid:false`。用户登出才调用 accounts `/oidc/end_session`，携带 id_token_hint、client_id 和已登记的返回地址，再清除 CoSpace 本地会话。

会话 authority 以 yucer ADR-036 和平台现有 session-status 实现为准：令牌过期只影响这一次 API 调用，不据此判断全局登录结束。中心明确回答无效才结束已有会话。080-rp 中较早的 back-channel logout 章节与 ADR-036 的轮询约定有演进差异；本项目采用中央查询主路径，暂不引入第二套相互竞争的登录判定器。

公开 issuer 与服务端 JWKS 网络地址分别配置，兼容容器内访问平台宿主机的情形，签名中的 iss 始终按公开 issuer 精确校验。平台目前没有在 access token 中给出组织冻结状态，不能由 account_status=active 推断组织可写；真实生产写权限接入前需联调平台状态查询或采用平台确认的替代契约。

## 5. 路由覆盖计划

I2 完成 RP 会话后，I3 将把适配器接入以下所有资源面。该表是装配要求，不是当前已生效的路由清单。

| 资源面 | 授权与归属要求 |
| --- | --- |
| `/api/projects`, `/api/spaces` 及详情 | 服务端先过滤授权空间；项目只暴露授权空间所需的父记录，不返回同项目其它空间 |
| 发布、候选、输入、批次列表与单项 | 每项重读保存归属，包含仅凭 ID 的直链；管理目录不能泄露其他用户记录 |
| `/publications/{id}/...`、`/candidates/{id}/...`、缩略图 | HTML/对象/点/范围查询检查 preview/query，ZIP 与可独立消费的几何下载检查 export；候选直接输出含资产须遵循相同规则 |
| 比较、核对、选择、关联派生 | 两个引用都检查空间归属；读比较与写核对区分；派生基线也须有权限 |
| 登记、预检、构建、批次变更 | 分别使用 data.manage/build.run，不从“可预览”推导写权限 |
| 发布、暂停/恢复、成果控制 | publication.manage；资料/候选控制按 data.manage/build.run，仍叠加原生命周期门禁 |
| 台账、对象和关系关联 | association.edit，校验所有引用来自同一空间或获准的本体资源 |
| 本体读取与校验 | 固定内置规则作为已登录用户的共享模板；工作区私有本体须有显式作用域。全局注册与编辑不能由某个空间 manager 推导 |
| 项目/空间创建与成员管理 | 需要工作区级产品管理授权和事务性归属创建；当前空间级 I1 不据此推导空工作区创建权限 |
| 根 `/api/preview`、`/api/query`、`/api/thumbnail` 与根静态 mount | 身份模式禁止旧无归属默认模型入口；可保留 workbench 登录和公开构建资源，不可用根静态别名绕过成果权限 |

权限门禁先于 poll、预检、生成离线包、读取几何和生命周期响应，覆盖 GET/POST/HEAD、Range、304、尾斜杠与路径规范化，未匹配的业务路由默认拒绝。API 无身份返回401，无权限统一403；不通过存在性差异返回其他空间的数据。鉴权后的暂停分发仍按原H3b语义拒绝。前端隐藏卡片不能代替直接URL授权。

`as_of/valid_until/completeness/grade` 等空间数据有效性字段不替代身份授权。离线包下载时检查权限；已经下载到机器人或其他消费端的副本不会因服务器撤权自动消失，离线有效期与设备信任需另外设计。

## 6. 当前实现与验收边界

本批代码位于 `packages/infrastructure/platform_identity.py`、`packages/service/space_access.py` 和 `packages/service/platform_resource_access.py`；策略契约为 `contracts/schemas/space-access-policy-v0.1.schema.json`。测试使用本地生成的 RSA 密钥和注入 JWKS，不访问真实 accounts，不保存密钥或 token。

通过的 I1 检查包括：真实 RS256 签名、issuer/audience/时间/租户字段、角色作用域、错误 kid 轮换、JWKS 不可用与非法 header、弱密钥和算法降级；多空间、跨组织/工作区、viewer/engineer/manager、workspace owner、保存记录归属、路径穿越和无轮询读取。I1 不等于真实登录成功，也不等于 HTTP 路由已经全部加门禁；这两项留在 I2/I3，并用隔离副本做双用户正负验收。
