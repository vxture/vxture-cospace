## 1. 实施方式

按通用核心本体、领域本体、场景实例三层组织，分批形成可检查成果。跨园区盘点先于单场景实现；场景用于验证覆盖和复用，不能独自决定所有概念。先固定语义和失败样例，再设计契约、实现内核与工作台。

本计划不替代现有 SG3 对齐/空间边界/连接核验、SG4 实例采用及正式发布、SG5 真实观测接入等独立验收。新增语义定义不会使这些缺口自动通过。

## 3. TO-01 盘点工作表

| 园区类型 | 必须分析的共性 | 主要差异与遗漏风险 |
| --- | --- | --- |
| 研发/办公型产业园 | 建筑、空间、公用设施、企业入驻、运营职责 | 多租户用途、办公与实验空间、共享设施 |
| 制造型工业园 | 建筑、设备、能源、环境与消防 | 生产设备、系统端口、功能网络、维护角色 |
| 仓储物流园 | 建筑、道路、出入口、设施、运营主体 | 仓储区域、装卸区、室内外衔接、动态对象 |

专业补充盘点包含洁净生产、专业储存等候选概念，仅表示覆盖需求；需专业资料和法规适用性评估后才能形成约束。首轮盘点不承诺建立全部行业设备词典或安全合规判定。

每条术语登记：来源术语、来源范围、业务含义、候选规范名、同义/歧义、L1/L2 归属、已有定义映射、正反例、所服务的问题、依据、责任人与未决状态。没有可验证用途或清晰边界的概念暂不进入固定版。

能力问题至少覆盖：对象是什么/在哪里、何种系统成员、实际连接为何、来源怎样报告、某时刻平台已知什么、谁承担职责、哪些对象受规则检查、哪些结论仍未知。每个问题映射到概念、关系、输入证据和预期回答，不先从界面字段反推本体。

## 4. TO-02 编制与评审清单

首轮候选核心组：对象与身份、空间、系统与组成、属性与量、功能与角色、时间与事件、观测与断言、证据与核验、业务主体。是否都实现为类在词典评审时决定。

首批领域深度：建筑/空间和室外设施先明确；供配电、给排水覆盖对象与参数、基本系统关系；消防、环境、运营覆盖设施、观测与职责语义。网络影响、安全判断、复杂生产过程只建立扩展边界，后续依资料深化。

交付词典不只列名称。每项需有定义、反例、属性关系和适用约束；同名定义、重复继承、非法端点、不明确单位和无依据推导要在评审中被发现。核心概念新增需说明跨领域必要性；行业术语优先留在 L2。

外部复用表逐项记录标准版本、候选概念、等价/宽窄/关联关系、冲突、许可证、采用/映射/自定义决定及理由。禁止只因标签相似声明等价。

## 5. TO-03 样例与失败矩阵

建立三个差异化合成场景，共用核心与领域模块的同一固定版本：

1. 研发产业园：办公空间、实验用途、共享公共设施和入驻企业。
2. 制造园：厂房、配电室、泵、跨空间系统成员和来源参数。
3. 物流园：仓储区、装卸区、室外道路、监测对象与安装位置不同的传感器。

样例使用相同概念复用，也包含各自专有模块；并非分别建立三套互不相干的词表。每份包含固定模块依赖、实例、必要几何/坐标声明、属性、关系、来源、核验、查询预期和能力限制。所有虚构数据明确标 synthetic，不登记生产规则库。

| 失败或边界用例 | 预期行为 |
| --- | --- |
| 核心模块引用领域模块、循环依赖 | 封存拒绝，定位依赖路径 |
| 同版本内容变化、依赖缺失、摘要错误 | 拒绝固定或消费，不回退其他版本 |
| 同名不同义、本地 ID 相同但模块不同 | 不自动合并；冲突/歧义可定位 |
| 旧设备词表 room 被当作通用房间 | 保留旧定义，要求显式映射及影响评估 |
| 数值缺单位、量种不符、非有限数值 | 按明确规则拒绝，原始来源声明可追溯 |
| 供电关系反向、监测关系端点不符 | 关系检查失败；不伪装为双向连接 |
| 跨层对象、管理分区交叠 | 按各关系族处理，不套用全局单父规则 |
| 最近邻设备匹配、未知类型 | 仅候选或未映射，不自动确认身份 |
| 没有备用电源记录 | 不推导“没有备用电源”；完整性不足单列 |
| 规则通过但无现场证据 | 表达合规与现场未核实分别返回 |
| 时效过期、来源冲突、迟到纠正 | 明确时态结果，可按发生/知晓时间复现 |
| 私有模块或无权场景被引用 | 服务端拒绝，不泄露私有内容及使用统计 |
| 离线缺传递依赖、未知必需语义 | 拒绝或明确能力不可用，不宣称完整支持 |
| 本体升级后读取旧发布 | 保持原定义；新规则不静默改变旧事实 |
| 角色变化、设备重建、实体拆分合并 | 保留历史与关联依据，不复用或猜测身份 |
| 空间连接被解释为设备可达 | 返回结构事实及限制，不输出通行保证 |

契约定稿须明确：IDL/JSON Schema 与领域校验各自覆盖什么、原始字节摘要与规范化摘要的区别、编译产物与定义包的绑定、存储提交可见性、并发修订、预算超限、恢复及旧版本回滚。不能依赖跨存储隐式事务。

## 6. 工作台与工程落位

先扩展现有语义本体工作面，区分核心/领域模块、定义详情、依赖、来源映射、校验、影响与固定版本；场景关联工作面选择配置集并实例化。地图展示实例，不承担共用定义编制。新导航与页面在语义和契约清晰后再设计。

复用现有领域模块和授权链路。源码中保存经检查的定义种子、契约和合成样例；正式封存内容和实例保存在运行数据中。凭据、台账原文、真实现场资料、认证状态和本机证据不得进入 Git。

实现批次使用 feature 分支/PR、五项必需检查与 squash merge。部署需另按现有部署文档核对 worker02，经标签镜像和 production Environment 审核；本规划不执行部署、不上传源码包。

## 7. 完成标准与衡量方式

不以概念数、图谱节点数或界面数量代表完成。重点记录：

- 能力问题是否可由固定定义与实例回答，无法回答的原因是否明确。
- 跨园区复用时新增了哪些模块、映射和实例，是否被迫修改核心代码或重定义含义。
- 概念冲突、未知类型、未映射、证据缺失和未核实分别有多少，覆盖分母是什么。
- 在线、人/机器视图与离线解释是否一致，旧版解释和迁移未决是否保留。
- 查询和校验耗时、包体和依赖规模在何种硬件、数据与预算下测得。

性能数值、领域准确率和真实交付完整率在资料与基准明确后制定，不在设计阶段编造百分比。每批状态以交付物、检查结果和未决清单为依据。
