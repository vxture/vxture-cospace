# 计算视图派生：技术路线与选型评估

日期：2026-11-16。状态：按用户明确的“态势底图”定位修订，供技术选型讨论，尚未冻结实现。

后续确认：用户已认可本产品方向，边界正式记录于 [ADR-006](../decisions/ADR-006-态势底图与设备决策边界.md)；数据模型、连接、派生、接口、存储、兼容及实施验收详见[态势底图计算视图技术设计](态势底图计算视图技术设计-v0.1.md)。技术候选仍需样板验证，不因边界确认自动成为已实施选型。

本次修订纠正上一版评估将设备通行规则、导航代价图和接近位姿生成纳入平台核心的偏差。CoSpace 负责描述空间事实；应用结合具身智能体的物理特性、感知能力和任务要求判断通行、规划与执行。不能因 CoSpace 没有导航规划器就认定态势底图架构不成立。

## 1. 产品边界与核心目标

计算视图是机器可读取、可查询、可关联的空间描述。它需要回答：这里有什么、在哪里、形状和尺度是什么、属于哪里、与什么相连、当前是什么状态、依据是什么、何时更新。

例如：建筑有多个楼层；楼层包含房间和楼道；楼梯连接楼层；门位于房间与楼道之间；配电柜安装在某房间某处。平台描述楼道几何与宽高、楼梯台阶几何、门洞和门扇、对象位置及状态。某机器人能否通过、应从哪里接近、怎样转向或跨越，由应用与机器人判断。

| CoSpace 态势底图 | 应用与具身智能体 |
|---|---|
| 几何、尺寸、空间边界、坐标基准 | 机体包络、运动能力与安全余量 |
| 楼层、楼道、楼梯、门、设备等类型与实例 | 针对任务理解哪些对象可作为目标 |
| 包含、相邻、开口、跨层连接等空间关系 | 结合设备约束推导可达性与导航图 |
| 开关状态、临时占用、观测时间与可信程度 | 决定是否重规划、避障、暂停或请求复核 |
| 基于几何和语义的范围、邻近、相交等查询 | 生成代价图、路线、轨迹、接近位姿和控制命令 |
| 固定发布、变更分发、在线与离线一致性 | 接受更新、任务版本策略与本地实时融合 |

平台可以保存外部系统提供的作业点或命名点，但要标明来源与语义；不能默认它是对所有设备都可达的停车点。通用 SDK 可提供读取与查询，设备导航适配属于下游集成，不反向定义底图事实。

## 2. 对当前实现的重新评价

当前“固定模型 → 分别派生人视图和计算视图 → 固定发布 → 在线/离线消费”的总体架构与产品定位一致。应重点判断空间描述是否足够完整、结构化和可信，而不是平台是否完成实机导航。

| 能力 | 当前检查结果 | 对底图的意义 |
|---|---|---|
| 几何与双视图共同来源 | 有冻结模型、摘要与坐标绑定 | 合理基础，应保留 |
| 表面空间查询 | 真实链以表面体素与 unknown 为主 | 能表示局部表面证据，表达能力仍有限 |
| 空间分区与离线消费 | 有预览实现及读取预算 | 有分发基础，规模与通用消费仍需验证 |
| 楼层/房间/楼道/楼梯/门的结构化表达 | 尚未形成完整真实派生链 | 是核心缺口，不是导航算法缺口 |
| 语义对象、本体与业务关联 | 有人工候选、点锚、固定快照和关系机制 | 能继续扩展，但点锚不足以完整描述对象空间范围 |
| 连接与空间拓扑 | 有对象关系声明基础 | 尚不能等同已验证的真实建筑空间连接图 |
| 占据/已观测空闲/未知 | 有合成契约，真实派生未打通 | 可作为空间证据组件，不应解释为设备通行结论 |
| 几何/语义质量与时效 | 有实验契约，真实验收仍不足 | 需要用于空间事实质量，不以实机导航作唯一判据 |
| 导航规划、机体通行判断 | 未形成完整链路 | 按明确定位，不属于平台核心缺项 |

关键代码依据：

- `packages/construction/preview_derivations.py`：冻结清单固定 spatial.npz；派生读取 points/colors；计算视图按 0.1 m 生成表面单元。
- `packages/construction/preview_model.py`：surface_cells 为坐标取整去重；不是建筑空间结构重建。
- `packages/construction/preview_semantics.py`：人工对象以模型点锚定，confirmation=unverified；已有本体和对象快照机制。
- `packages/spatial/preview_range.py`、`packages/views/agent/partitioned_preview.py`：只描述表面证据，无证据处为 unknown。
- `packages/views/agent/voxel.py`：占据编码试验使用合成数据，不能证明真实观测融合已完成。
- `packages/construction/preview_lidar_mapping.py`：当前短序列配准仍有回环、全局对齐、去畸变等限制；这些影响底图几何可靠性。
- `packages/spatial/quality_contract.py`：实验质量元数据，不是生产质量门禁。

这些发现说明当前计算视图应从“表面索引”升级为“几何—语义—空间结构—状态”联合表达。robot_ready=false 不能单独衡量底图是否完成；未来应按组件、范围和用途说明质量与能力。

## 3. 推荐的数据表达：三维语义空间图与几何证据结合

不在体素、网格、场景图之间只选一个。它们分别描述形状、实体与关系，应通过稳定身份和坐标绑定。

### 3.1 统一坐标与几何层

保留实测点云或网格、局部空间坐标、重力方向、尺度、各来源的配准变换与不确定性。多楼层使用真实三维关系，不把同一 XY 上的楼道压成一层。

几何载体按用途选择：点云适合保存测量表面；网格便于描述连续面和结构；体素适合局部状态与空间查询。包围盒是粗略范围，不可替代精确形状，且倾斜构件宜区分轴对齐盒与有向盒。

可提供几何距离、相交、局部截面、表面法向等通用查询，但不返回未经机体约束验证的“可通过”。距离场也是可选几何加速表达，不是底图成立的必要条件。

### 3.2 建筑空间结构层

建议以建筑/区域、楼层、空间单元、结构构件、开口与连接构件、设备对象组织表达。层级是分类与关系，不必将所有对象强行塞进单一树。

| 对象 | 建议表达 |
|---|---|
| 楼层 | 稳定身份、标高、范围、楼层命名与所属建筑 |
| 房间/楼道 | 类型、三维范围、边界与所属楼层；必要时提供沿程截面 |
| 墙/楼板/立柱 | 形状、边界、厚度等有证据的属性 |
| 楼梯 | 楼梯段、平台、连接楼层、台阶几何、坡度与扶手等可观测信息 |
| 门 | 门对象、门洞、门扇几何、关联两侧空间、开启方向与状态来源 |
| 电梯 | 井道/轿厢或站点等必要对象、服务楼层、外部系统提供的状态 |
| 配电柜等资产 | 类型、实例 ID、形状/范围、位置朝向、安装或所属空间、外部资产引用 |

尺寸需要注明定义、测量方法与误差。例如门洞宽度、门扇角度和当前开口净宽是不同属性；楼道某截面宽度不等于全程最小宽度。几何无法可靠测得的值保留未知，不根据类别名称编造。

### 3.3 空间关系与连接层

建议支持包含、位于、相邻、开口连接、跨层连接、安装于等明确关系，并保留几何证据与核实状态。

例如：楼梯连接一层与二层，这是建筑空间连接事实；是否适合某轮式或四足设备，由下游判断。门连接房间和楼道，不代表门当前打开，更不代表每种设备都可通过。拓扑连接、实时状态、设备可达性必须分开。

### 3.4 语义与身份层

沿用现有本体、实例、业务绑定框架，补齐对象范围、层级与空间关系。对象 ID 不绑定点索引或网格片段；重新建图时进行实例关联，不能每次生成一套全新资产身份。

几何片段可以变化，设备身份应尽可能稳定。对拆分、合并、移动、删除保留明确版本关系；无法确定是否同一对象时保留候选匹配，不静默归并。

### 3.5 状态、证据与版本层

区分长期结构与短期态势，例如门存在是结构事实，门打开是带时间的状态；某处有临时堆物是动态观测。每项状态记录观测时间、接收时间、来源、适用范围和时效，不能用最近一次平台发布时间冒充最近现场观测。

区分实测、设计资料、人工确认、算法推断与外部系统同步。几何、类别、身份和状态可有不同可信程度，不使用一个总分掩盖差异。

## 4. 推荐派生流程

1. 资料归一：检查单位、坐标、标定、轨迹与来源；区分实测资料和设计资料。
2. 几何构建：配准、去噪、建立子地图/表面，并保存构建依据。
3. 结构识别：提取楼板、墙、开口、楼梯等，划分楼层与空间单元。
4. 语义实例化：识别设备与构件实例，关联本体、既有资产身份和空间范围。
5. 关系建立：构造包含、相邻与连接等关系，检查几何一致性与规则。
6. 人工核对：优先核对关键连接、对象身份与算法不确定项；不要求所有几何人工重画。
7. 固定发布：冻结几何、语义、关系、状态截面、质量与来源引用。
8. 用途分发：输出所需几何、语义、结构和状态组件，由应用按设备能力消费。

不是所有输入都具备同等自动识别能力：纯 XYZ 点云缺少纹理与外观信息，对配电柜类别识别通常比有 RGB/图像或资产台账更困难。BIM 可带结构和语义，但必须检查与现场的对齐与差异。

自由空间需要观测射线与位姿等证据；仅有最终点云不能可靠推出。平台若发布该组件，应固定关联可重放观测和标定资料，不必把原始资料全部交给机器人。若应用只需表面几何和结构语义，不必强制生成所有体积组件。

## 5. 技术选型

| 层次 | 选项与建议 | 边界 |
|---|---|---|
| 点云/网格处理 | Open3D、PCL 等作为算法组件候选 | 工具库不自动完成建筑结构与语义识别；需目标场景比较 |
| 建筑结构表达 | 参考 IFC 的建筑构件语义、IndoorGML 的室内空间与连接思想 | 不要求内部模型完整照搬；门/空间/构件的语义要明确，不能只有模型文件转换 |
| 三维场景图 | 最小自有领域模型，参考 Spark-DSG / Hydra 的分层场景图 | 推荐作为核心表达方向，研究实现需评估后选择性复用 |
| 语义识别 | 三维语义/实例分割，或二维识别后投影融合 | 需要图像、位姿、跨帧实例关联与误差处理；按对象类型评测 |
| 开放词汇理解 | ConceptGraphs 等作为辅助路线 | 适合检索与提出候选；关系、身份和几何仍须核实 |
| BIM 接入 | IFC 构件与空间解析、现场坐标对齐 | 设计结构与实测结构分源保存，不能把设计图默认当现场现状 |
| 占据表示 | OctoMap 等作为可选观测组件候选 | 发布空闲/占据/未知空间证据，不定义机体通过性 |
| 表面融合/距离 | nvblox、Voxblox 等按实际需求评估 | 可增强几何与查询；不是首期必须全部引入的核心框架 |
| 大规模体积 | OpenVDB/NanoVDB 等在规模瓶颈时评估 | 数据组织技术，不替代语义实体与空间关系 |
| 导航消费 | Nav2、厂家导航 SDK 等作为下游验证端 | 检验底图是否容易消费；不把规划器纳入平台核心能力判定 |

推荐首批聚焦：可靠几何与坐标 → 楼层/空间/门/楼梯结构 → 资产实例与空间绑定 → 可查询的连接图 → 质量与版本。开放词汇模型辅助识别与检索，结构化空间事实承担稳定交付。距离场、细粒度占据和高级重建按应用需求增加。

这些是选型候选，不是已经完成统一数据、统一硬件的算法性能结论。正式引入需检查维护、依赖、许可、硬件要求与商用模型权重条款。

## 6. 存储与服务

关系数据库保存场景、楼层、空间实体、对象身份、关系、发布索引和质量元数据；几何和大规模体积组件放不可变分块成果存储，二者通过固定身份与摘要关联。是否采用图数据库由查询负载决定；场景图是一种领域表达，不要求立即增加图数据库。

人视图和计算视图共用权威来源，但计算视图不依赖展示截图、浏览器运行时或展示纹理。轻量 SDK 提供组件读取、坐标变换及空间查询，机器人无需安装整个平台。

建议查询能力：

- 某楼层有哪些空间、楼梯、门和资产。
- 给定位置属于哪个空间，附近有什么对象。
- 某设备对象的范围、位置、朝向、类型和资产身份是什么。
- 两个空间通过哪些开口或跨层构件连接。
- 某条楼道的几何边界、局部截面与相关观测是什么。
- 对象或空间在两个发布间发生什么变化，哪些事实仍未核实。

返回固定发布、坐标、单位、来源、观测时间与质量；未知、未提供、过期与范围外应明确区分。平台接口不必接受机器人机体参数才能回答这些问题。

## 7. 验收与推进建议

首个真实样板以“两层空间、楼道、楼梯、门、配电柜”为目标，而不是先以某机器人导航成功为平台唯一验收标准。

1. 几何正确：独立检查尺度、标高、楼层归属、开口与构件边界；明确误差与未覆盖区。
2. 结构正确：楼层、空间单元、楼梯与门均可查询；多层空间不混叠。
3. 语义正确：核实对象类别、实例身份、位置范围和业务绑定，统计漏检与误识别。
4. 关系正确：包含与连接有证据；没有因空间重叠、点云孔洞或名称相似生成错误连接。
5. 状态可信：观测时间和来源明确；静态构件与动态状态分离；推断与确认分开。
6. 版本稳定：重建后对象身份可追溯；几何、语义与关系快照一致；变化可定位。
7. 消费方便：两个不同能力的应用/设备读取同一底图，各自作出通行判断，无需平台维护两套事实。

实机抵达可作为下游集成验证，能够暴露几何、关系与接口不足，但不能把应用规划错误直接归为底图算法失败，也不能用一次实机成功替代完整空间描述验收。

是否领先，应比较结构理解、实例稳定性、空间关系准确性、变化更新、证据可追溯及跨应用复用，而不是比较平台自带多少导航算法。当前双视图和版本架构合理；真正需要补强的是结构化空间理解及真实质量验证。
