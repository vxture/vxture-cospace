# 项目目录结构设计

版本：v0.4\
日期：2026-10-26\
状态：已确认的目录基线；后续实现按需创建目录\
依据：[总体架构](总体概要技术架构设计-v0.1.md)、[总体模型](真值与两类视图总体模型设计-v0.1.md)、[实施规划](总体设计与渐进实施规划.md)

## 1 组织原则

采用单仓库，围绕“真值构建”和“真值＋两类视图的空间态势服务”组织产品代码。真值资产、生命周期管理、外部适配及技术基础各有明确归属。首版允许模块化单体与独立算法进程协作，不将代码目录等同于微服务或部署单元。

应用负责装配与交互，领域模块负责产品规则，契约负责跨边界交换，适配器负责技术转换。产品模块目录优先采用单个英文小写词，不使用连字符；文档标题可使用中文。暂不确定前后端框架、核心语言、包管理器或数据库。

目录命名统一为`spatial`（原truth，曾拟名model）和`views/agent`（原views/machine）。spatial明确表示权威空间模型模块，负责几何、坐标、覆盖、空间对象及质量，避免通用model名称的歧义；agent表示面向机器人智能体的视图模块。技术概念仍使用“真值”“人视图”“机器视图”；本次目录调整不变更契约中的真值版本身份或视图种类取值。

目录是职责边界；语言包、编译目标及工作区配置在技术栈确定后落位。不同语言可以在一个职责目录内按需建立子包，但不能为每种语言复制一套独立产品模型。

## 2 总体目录

以下为目标结构。除现有内容及本轮文档外，所列目录均为规划，按实际增量创建，不一次生成全部空目录。

```text
vxture-cospace/
├── README.md                       # 项目入口、阶段状态、文档导航
├── .gitignore
├── docs/                           # 产品、设计、决策、验证与交付说明
│   ├── product/                    # 产品定义、用户任务、范围与路线
│   ├── architecture/               # 总体架构、模型、目录与专题技术设计
│   ├── decisions/                  # 有编号的技术决策记录
│   ├── validation/                 # 跨模块验收方案、结论及证据索引
│   ├── guides/                     # 开发、操作、部署与交接手册
│   └── references/                 # 原始输入资料，保留来源与原貌
├── contracts/                      # 跨边界数据与接口的规范源文件
│   ├── schemas/                    # 真值、视图、发布、质量等清单模式
│   ├── api/                        # 服务接口规范，协议选定后落地
│   └── compatibility/              # 契约版本及兼容、升级规则
├── apps/                           # 可启动应用，只承担装配及应用层职责
│   ├── workbench/                  # 内部交付工程师工作台
│   ├── api/                        # 空间服务与工程操作的网络入口
│   ├── worker/                     # 构建、派生与校核任务的执行入口
│   └── cli/                        # 本地校验、离线包与工程命令入口
├── packages/                       # 可复用产品模块
│   ├── spatial/                      # 权威空间内容、身份、坐标与质量模型
│   ├── data/                       # 数据管理平台：资料、数据集、成果登记与血缘
│   ├── ontology/                   # 语义本体平台：类型、属性、关系、约束与版本
│   ├── construction/               # 资料预检、构建编排、候选与诊断
│   ├── views/
│   │   ├── human/                  # 人视图派生、表达与质量传递
│   │   └── agent/                  # 面向智能体的机器视图、空间表达与定位参照
│   ├── service/                    # 发布解析、查询、分发与一致性规则
│   ├── lifecycle/                  # 审核、版本、发布、更新、撤回与证据管理
│   ├── adapters/                   # 算法、传感格式与外部系统的适配
│   └── infrastructure/             # 存储、队列、身份接入、日志等技术实现
├── sdk/                            # 经消费验证后提供的客户端读取与调用库
├── configs/                        # 可版本化的配置模板与配置模式
├── deploy/                         # 容器、部署、环境与安装资产
├── scripts/                        # 仓库开发、检查、打包及维护脚本
├── tests/                          # 跨模块、端到端及契约兼容性验证
├── examples/                       # 小型合成样例、调用示例与预期结果
├── experiments/                    # 算法探索、资料核验与可复跑试验
│   ├── README.md
│   ├── scripts/                    # 仅服务于试验的工具
│   ├── templates/                  # 试验登记模板
│   ├── evidence/                   # 上游资料快照、来源及摘要
│   └── runs/                       # 本地试验输出，按单次运行留痕
└── third_party/                    # 第三方来源、固定版本及许可登记
```

仓库名称沿用`vxture-cospace`。目录规划不决定最终产品名称，也不代表其中每项能力均纳入首版交付。

## 3 产品模块的职责边界

| 目录 | 负责 | 边界 |
|---|---|---|
| `spatial` | 真值内容、对象身份、空间坐标、覆盖与质量的共同语义及内容约束 | 不执行SLAM，不操作当前发布指针 |
| `data` | 资料与成果登记、数据集版本、内容引用、来源、血缘及保留规则 | 不自行采用候选或维护另一份正式发布状态；底层存储由infrastructure实现 |
| `ontology` | 类型、属性、关系、约束、外部类型映射及本体版本 | 不直接拥有现场实例及其位置；本体升级不自动修改旧真值 |
| `construction` | 输入要求、预检、构建步骤、候选成果和过程诊断 | 调用算法适配器，不直接授予候选正式真值身份 |
| `views/human` | 面向人的派生内容、简化表达、质量图层及损失声明 | 工作台页面归workbench；视图编辑形成反馈而非直接改写真值 |
| `views/agent` | 占据与未知表达、局部几何、索引及重定位参照 | 机器人控制不属于该模块；定位适用性须另行验证 |
| `service` | 固定发布组合的读取、空间与对象查询、分发、追溯及有效性检查 | 不静默选择构建过程地图，不替代审核发布流程 |
| `lifecycle` | 场景配置管理、校核审核、版本采用、发布切换、更新影响、限制与撤回 | 质量数据结构归spatial；校核结论和证据组织归本模块；重计算委托construction或views |
| `adapters` | 外部观测格式、算法进程、BIM及外部资产系统转换 | 不为适配某个算法重定义正式真值，不夹带客户业务流程 |
| `infrastructure` | 领域所需存储、任务执行、权限、审计及可观测性接口的技术实现 | 不承载空间语义或发布采用规则 |

真值清单与质量含义的领域规则放在spatial；清单交换格式的规范定义放在contracts。两者通过契约校验与一致性检查保持同步，避免出现两份各自演进的字段规范。

算法适配按需采用`packages/adapters/algorithms/<implementation>/`；传感消息适配采用`packages/adapters/observations/<format>/`。候选名字不提前成为产品一级目录。原版、ROS2移植版与自有修改版分别登记来源和提交，不按同名算法混用。

## 4 依赖与装配规则

依赖方向按实际调用说明如下：

1. spatial是空间领域基础，不依赖construction、views、service或lifecycle。
2. construction与两类views依赖spatial，通过接口使用算法和存储能力。
3. lifecycle调用构建、派生及质量检查能力，负责受控采用和发布；它不嵌入具体算法代码。
4. service读取固定内容及发布、有效性记录，不反向触发审核或修改真值。发布及有效性读取接口由其消费方定义，由应用装配提供实现，避免service与lifecycle循环引用。
5. adapters与infrastructure实现领域边界所需接口；领域模块不直接导入具体数据库、ROS消息类型或第三方算法内部类。
6. apps组合模块与技术实现。workbench通过接口执行工程操作，不直接读写正式资产存储。worker负责任务进程入口，调度规则仍归相应模块。
7. sdk依赖公开契约及必要的轻量读取能力，不依赖应用入口、内部数据库结构或构建环境。

公共代码先放入真正拥有它的模块。仅在跨模块确有稳定共用且无业务归属时再提取小型基础包，不预设无边界的common、utils或platform目录。

data与ontology作为同级领域支撑模块，详细边界和阶段计划见[数据管理与语义本体平台规划](数据管理与语义本体平台规划-v0.1.md)。跨模块通过固定引用与接口协作；spatial不依赖本体平台运行数据库，data不导入所有产品实体形成循环引用。工作台按需增加数据管理与语义本体功能区，共用API和运行基础。

## 5 契约、配置与第三方内容

| 内容 | 归属与规则 |
|---|---|
| 跨进程及交付清单格式 | contracts；每项标明版本，不按人视图和机器视图复制真值定义 |
| 语言绑定、生成客户端 | 在所属模块或sdk的构建输出生成，标明来源，避免手工修改生成文件 |
| 示例包 | examples；保持小体积，明确synthetic及支持的契约版本 |
| 算法比较参数 | experiments；形成产品选项后，经验证再提升至configs |
| 可交付配置模板 | configs；区分构建、派生、服务和部署引用，不含现场凭据 |
| 容器与构建环境 | deploy；试验专属环境可先留在experiments，验证后再提升 |
| 第三方源码 | 默认通过固定依赖获取；确需随仓库保存时放third_party并保留许可和修改记录 |
| 第三方登记 | third_party；记录组件、固定提交、来源、许可、依赖与采用状态。原始核验快照继续留experiments/evidence |

产品源代码许可与第三方组件许可分别确定，不因目录创建而自动选择本产品的开源许可证。对外发布时按实际组件组合生成依赖与许可清单。

## 6 代码仓库与运行数据分离

大型观测日志、候选、正式真值、派生视图、运行数据库及客户资料放在配置指定的数据根目录。数据根目录可位于仓库外；本地开发若使用仓库内`var/`，整个目录应被忽略。

运行数据建议按以下逻辑组织；这是本地文件存储布局建议，后续对象存储可沿用身份与清单关系，不把物理路径当作产品ID：

```text
<data-root>/
├── ontologies/<ontology-id>/<version>/ # 正式本体包及不可变快照
├── scenes/<scene-id>/
│   ├── observations/<acquisition-id>/
│   ├── references/<reference-id>/
│   ├── candidates/<candidate-id>/
│   ├── spatial/<truth-version-id>/
│   ├── views/<view-version-id>/
│   ├── releases/<release-id>/
│   └── evidence/<record-id>/
├── jobs/<job-id>/                   # 临时工作目录和任务日志
├── state/                          # 当前发布指针、有效性与其他可变运行记录
└── cache/                          # 可从固定来源重建的缓存
```

正式真值、视图和发布内容写入完成后不可覆盖。state记录与不可变清单分开管理，通过受控切换关联。jobs及cache不作为正式服务隐式依赖；可清理不代表必要观测或校核证据可清理。

experiments/runs保留本地试验结果；仅将可审查的小型报告、摘要和配置纳入版本控制，原始bag及大型生成物不提交。正式发布包与安装产物输出到被忽略的dist或外部交付目录，发布说明与验证结论保存在docs中。

## 7 测试及文档归属

模块内部规则的测试与代码就近存放；tests只放跨模块集成、契约兼容和端到端验证。合成测试资料可就近存放；具有用户参考价值的完整样例统一放examples，避免复制多份来源不明的基准数据。

docs/architecture保留技术设计，docs/decisions记录关键取舍及重审条件，docs/validation记录验收结果并链接运行证据。试验报告不能代替正式能力验收。工程操作及恢复手册放docs/guides。

本轮不批量迁移既有架构文档。当前位于architecture的验收矩阵及采集需求继续使用原路径，后续确需迁移时更新所有引用，并保留迁移记录。

## 8 现有内容与渐进落地

| 当前内容 | 本轮处理 | 后续归属 |
|---|---|---|
| 根目录两份原始Word文档 | 保留，不改内容和位置 | 经统一更新引用后迁入docs/references |
| docs/architecture | 保留，新增本设计 | 继续作为技术设计入口 |
| experiments/scripts | 保留试验用途 | 稳定输入检查能力经测试后提升至construction或观测适配；试验脚本改为调用产品实现 |
| experiments/evidence、templates | 保留 | 不混入正式真值或产品配置 |
| 最小契约Markdown草案 | 保留设计解释 | 实现时在contracts形成机器可校验规范，两者同步维护 |

目录落地按以下次序执行：

1. 职责和命名已审定，已建立README导航；既有文件保留原位。
2. 下一个样例闭环按需创建contracts/schemas、examples、packages/spatial、packages/service及apps/cli，落地清单校验与固定版本查询。为验证而手工准备的两类视图须明确标记，不声称已实现真实派生。
3. 真实算法接入时创建construction、adapters及worker，并按实际路线补充环境配置；稳定试验能力提升后删除重复实现或保留兼容入口。
4. 按实际消费需求增加两类视图派生、lifecycle、工作台、网络入口及SDK，不提前搭建所有入口或服务。

后续若变更一级职责或依赖方向，先更新本设计并记录决策。语言内文件布局、构建脚本等常规细节在各模块细化，不需要反复调整项目一级目录。

## 9 基线确认与当前落地

用户已确认单仓库目录方案及`spatial`、`agent`命名。首批建立contracts/schemas、packages/spatial、packages/service、apps/cli、examples及tests，随后补充data与ontology。已实现离线合成服务包校验入口，验证范围见[记录](../validation/合成服务包校验记录-2026-10-26.md)，不代表完整产品可用。

下一增量将最小清单契约转换为机器可校验规范，用合成样例检查来源、坐标、版本及产物摘要关系，再通过CLI提供本地校验入口。目录基线不构成技术栈或存储选型结论。

本轮补充data与ontology两个平台模块及职责说明，下一轮最小契约同时覆盖资料登记和固定本体引用；其他平台能力按阶段扩展，不提前生成全量子模块。
