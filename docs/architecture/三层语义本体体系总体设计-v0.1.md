日期：2026-11-19。状态：三层方向经用户确认；本文为规划设计草案，具体词表、字段、契约和实现批次待逐项验证，不代表已实现或已部署。

2026-11-20 产品边界补充：语义本体定位于“公共资源”，按未来独立通用产品建设，见 [ADR-007](../decisions/ADR-007-语义本体独立产品边界.md)。通用内核和 UI 不反向依赖 CoSpace；L3 由消费方持有，第三层不意味着本体模块拥有场景实例库。

## 1. 产品目标与设计决定

CoSpace 建设以空间为组织基础、可供不同园区和应用共同引用的语义体系。首批服务产业园区、工业园区，长期支持建筑群、工厂及基础设施。态势地图是空间事实的交互与消费入口，本体同时服务结构化查询、外部系统对齐和智能体理解。

采用三层语义架构：

| 层级 | 核心问题 | 维护内容 | 不承担的内容 |
| --- | --- | --- | --- |
| L1 通用核心本体 | 如何一致描述空间与现实系统？ | 跨领域概念、属性和关系的基础语义、时间与证据模式 | 某园区对象、专业设备大全、具体业务阈值 |
| L2 领域本体 | 某专业领域有哪些对象、关系和规律？ | 建筑、供配电、消防等可组合模块及专业约束 | 各园区实际设备、实时数据、私自重定义核心概念 |
| L3 场景实例与事实 | 某个现实场景实际有什么、依据是什么？ | 对象、几何、属性断言、关系、观测、事件、业务配置和来源 | 改写引用概念的含义、将现场特例提升为普遍规律 |

前两层共同属于本体定义，第三层是引用这些定义的实例知识。三层不是三套部署、三个数据库，也不要求每个对象都经过 L2 才能引用 L1。

设计决定：

1. 从多类园区提取概念并集，经归并和语义协调形成体系；不围绕某一个项目反推全部定义，也不只保留所有园区共有的概念交集。
2. L1 精炼稳定，L2 模块化扩展，L3 承载现场差异。分类、组成、位置、功能、角色分别建模。
3. “工业园区”“物流园区”等应用配置集选择领域模块和适用约束，不复制一套本体，不增加第四语义层。
4. 源资料声明、本体定义、映射提案和场景采用分别管理。规则通过不等于现场属实。
5. 类型、关系、断言、观测及派生结论均可追溯；历史解释绑定固定依赖，不读取 latest。
6. 初期继续采用版本化 JSON 与确定性校验；是否引入 RDF/OWL、SHACL 或图数据库由互操作、推理和负载验证决定。

## 2. 行业依据与适配原则

| 参考 | 已有做法 | 本项目借鉴与限制 |
| --- | --- | --- |
| [ETSI SAREF](https://saref.etsi.org/) | 核心本体与能源、建筑、环境、制造等领域扩展，模块分别版本化 | 借鉴模块组织、复用和扩展；不能假定完整覆盖空间几何与园区业务 |
| [IOF](https://www.industrialontologies.org/) | 共享工业参考本体，模块化派生领域或应用本体 | 借鉴工业概念协调与治理；不宣称采用了其完整体系 |
| [BFO](https://basic-formal-ontology.org/) | 高度抽象的上层本体 | 借鉴对象、过程、角色等区分；CoSpace 核心是工程核心，不必覆盖全部知识领域 |
| [BOT](https://w3c-lbd-cg.github.io/bot/) | 建筑拓扑最小可扩展核心，社区组草案 | 参考空间、构件和拓扑；不以此替代实测几何或宣称标准符合性 |
| [Brick](https://brickschema.org/) | 建筑设备、系统、点位及其关系的共享语义 | 评估设施与监测点映射，避免按厂商名称重复建类 |
| [SOSA/SSN](https://www.w3.org/TR/vocab-ssn/) | 区分传感器、被观测对象、属性、过程和结果 | 参考观测模型，不直接把传感器位置当作被监测对象 |
| [OWL 2](https://www.w3.org/TR/owl2-overview/) / [SHACL](https://www.w3.org/TR/shacl/) | 分别表达形式语义及 RDF 数据约束 | 区分语义推理与交付完整性检查；采用技术前先明确支持子集 |
| [Azure Digital Twins](https://learn.microsoft.com/en-us/azure/digital-twins/concepts-models) | 模型定义与具体孪生对象分离 | 支持定义与实例边界，不将其直接等同完整三层本体 |
| [Palantir Ontology](https://www.palantir.com/docs/foundry/ontology/overview/) | 对象、关系及动作、函数、治理组成运营层 | 为未来应用和动作契约预留语义；不据此扩大设备控制边界 |

以上是架构参考，不是已完成的集成清单。每项外部复用须记录精确版本、概念匹配程度、许可证和依赖。区分等价、较宽、较窄及关联映射；近似对应不能声明语义等价。IFC、GIS 和台账也不是本体的替代品。

## 3. L1 通用核心本体

以下为候选概念组，不是已发布类名。先定义含义和边界，再决定哪些是类、属性、关系或契约记录，不把每个名词都做成类型。

| 概念组 | 候选内容 | 关键区别 |
| --- | --- | --- |
| 对象与身份 | 实体、物理对象、信息对象、外部记录引用 | 现实对象、数字记录、几何表达不是同一身份 |
| 空间 | 空间区域、位置、边界、空间参照、拓扑连接 | 物理空间、管理范围、坐标表达分别定义 |
| 系统与组成 | 系统、组成、成员、端口、连接 | 系统成员、物理部件、空间包含不能合并 |
| 属性与量 | 属性定义、量种、值域、单位、量测定义 | 额定参数、实测值、派生值不同义 |
| 功能与角色 | 功能、能力契约、角色指派 | 设备是什么与它承担什么角色分开 |
| 时间与活动 | 时刻、区间、过程、事件、有效期 | 事件发生、观测发生、平台知晓时间分开 |
| 观测与声明 | 观测对象、被观测属性、结果、方法、断言 | 来源报告、核实事实、推导结论分开 |
| 证据与评估 | 来源、证据引用、核验、质量维度 | 完整性、真实性、精度、时效分别评估 |
| 主体与职责 | 组织、业务主体、职责指派 | 现实组织与平台租户/权限主体分别关联 |

L1 入选条件：含义在多个领域中稳定，或为时间、身份、证据等跨领域机制所必需；不依赖某厂商、某园区或某项临时业务政策。未满足时先保留为 L2 候选。

身份规则：名称不作身份；稳定标识不得复用；类型身份与版本分离。场景对象采用作用域加稳定实体 ID，跨场景引用显式携带作用域；未来可经核实绑定园区级对象注册身份，不默认同名或同资产号即同一对象。

同一实体可以有多个类型，但组合必须相容；类型特化须明确继承语义与冲突规则。角色指派独立携带范围和有效期，不能通过不断增加“消防巡检备用水泵”等组合类型表达。

## 4. L2 领域本体模块

| 模块候选 | 主要内容 | 首批深度 |
| --- | --- | --- |
| 建筑与空间 | 园区物理范围、地块、建筑、楼层、房间、开口、门、楼梯、空间用途 | 优先定义，衔接现有结构与几何 |
| 室外设施 | 道路段、出入口、围栏、停车区域、公共设施 | 首批定义关键空间和拓扑，不承诺道路导航 |
| 供配电 | 配电柜、回路、电气端口、额定参数、供电关系 | 设备与参数优先，网络推导另行验证 |
| 给排水 | 泵、阀、管段、储水设施、介质和连接 | 设备与系统成员优先 |
| 安全消防 | 消防设施、防火分区、告警及检查语义 | 设施定位优先，合规判定需专业依据 |
| 环境与监测 | 温湿度、水位等被观测属性、监测点、程序与结果 | 在通用观测模式上特化 |
| 组织与运营 | 入驻、维护、管理、巡检对象、工单和业务记录引用 | 职责关系及引用优先，不替代外部主系统 |
| 生产与仓储物流 | 生产设备、工位、仓储区、装卸区及专业过程 | 首轮盘点覆盖，后续按资料与需求扩展 |

行业特有概念，如洁净室和专业储存设施，在相关领域模块内扩展。新模块须给出适用范围、定义依据、与既有概念的区别和依赖，不能以交付紧急为由重复定义核心概念。

模块依赖方向：L2 可引用 L1 及明确声明的 L2 模块，L1 不反向依赖 L2。发布依赖图必须无环。多个领域共享的新概念经评审决定是否上移核心，不能复制同名定义。

跨领域桥接模块仍属于 L2，用来表达已明确的领域间关系。优先由消费模块引用窄接口，避免建筑、能源、消防模块互相全量导入。

园区配置集固定模块清单、选择的约束与规则及其参数要求。不同园区可以采用不同配置集；配置集不能放宽概念的固有含义。法规适用性依辖区、时间、用途和权威依据确定，不内置为全局真理。

## 5. 定义编制规范

每个概念定义至少包含：稳定 ID、标题及同义名、规范性定义、正反例、所属模块、适用范围、定义依据、维护责任、版本和弃用状态。

属性另需：允许主体、数据类型、量种、单位策略、枚举/值域、基数、是否适用于静态参数或动态观测、是否允许未知及缺失的处理。不能用字符串保存所有数值后宣称支持单位计算。

关系另需：源/目标或各端角色、方向、对称性、基数、是否可传递、逆关系、适用时间和证据要求。未明确声明的传递性不能由查询器自行假定。

| 容易混淆的语义 | 设计要求 |
| --- | --- |
| 房间与设备间 | 房间是空间概念，设备用途可通过用途指派或经定义的特化表达；首轮词典统一选择，不按名称猜测 |
| 楼层与楼板 | 前者组织空间，后者是物理构件 |
| 空间包含与业务归属 | 分别检查，允许管理分区交叠，单父只约束明确的层级关系族 |
| 物理组成与系统成员 | 部件拆装与功能系统归属分别记录 |
| 门洞、门扇、门状态 | 几何尺寸、物理构件、时态报告分开 |
| 安装位置与监测对象 | 传感器安装于 A，不代表只监测 A |
| 资产与设备 | 物理设备关联资产主记录，资产身份不替代实体身份 |
| 巡检点与设备 | 巡检点是业务指定目标/位置，设备可被指定为巡检对象 |

语义并集流程：跨园区资料采样 → 候选术语登记 → 同义/歧义归并 → 概念与角色划分 → 核心/领域归属 → 属性关系与约束 → 样例与反例 → 评审固定。每个未决项记录理由，不强制近似归类。

## 6. 约束、规则与未知

| 种类 | 意义 | 示例 |
| --- | --- | --- |
| 语义公理 | 概念必然具有的逻辑含义 | 经定义的水泵类型属于设备 |
| 数据约束 | 在指定交付范围内必须满足的表达要求 | 某类量测必须有单位与方法 |
| 推导规则 | 在明确前提下产生派生结论 | 对声明可传递的组成关系展开成员 |
| 业务政策 | 按范围、时间及参数生效的处置规则 | 指定区域温度阈值告警 |

定义和适用方式位于 L1/L2；L3 保存规则选择、实际参数、输入与执行结果。规则包是治理与交付单元，不增加语义层。规则须声明类型、输入、适用范围、缺失处理、输出、优先级/冲突策略、终止或计算预算和版本。

开放知识与交付完整性分别处理：未记录备用电源不等于无备用电源；交付检查可在明确范围中要求填写该信息。unknown、unobserved、unverified、expired、conflict、not_applicable 和 unavailable 是不同维度的候选状态，最终编码需映射现有协议，不能强行折叠为一个布尔值。

推导结果必须引用规则、输入快照、参数与方法，不覆盖原始断言。供电影响分析需网络配置、开关状态及分析假设；空间邻近和图上连接均不能单独证明故障影响。规则校验通过、形式一致、现场核实和适用性验收分别报告。

## 7. L3 场景实例与事实

物理园区、平台 Workspace、业务场景、几何坐标系是不同概念。一个园区可由多个场景表达；一个 Workspace 可管理多个园区；现实职责关系不自动授予平台权限。

| 逻辑记录 | 关键内容 | 归属与约束 |
| --- | --- | --- |
| 实体 | 稳定身份、类型引用、修订、生命周期 | 场景事实；几何重建不自动更换实体身份 |
| 几何表达 | 对象引用、用途、编码、坐标、误差、来源 | 一个对象可有多种表达；点锚不等同边界 |
| 属性断言 | 主体、属性、值、单位、有效时间、来源、核验 | 设计值、铭牌值、实测值并列，按显式策略读取 |
| 关系与端口连接 | 端点角色、关系类型、有效期、证据、修订 | 二元关系和多端连接分别定义 |
| 角色/职责指派 | 对象、角色、主体、适用范围和时间 | 业务职责不替代鉴权 |
| 外部绑定 | 外部系统与记录身份、匹配依据、状态 | 确认绑定与可能匹配分开 |
| 观测 | 对象、属性、结果、方法、来源、观测/接收时间、有效期 | 追加纠正；时序正文可外置，语义引用可追溯 |
| 事件与业务引用 | 主题、发生时间、位置、状态、外部记录引用 | 告警报告不自动变成已确认事故 |
| 派生结论 | 输入快照、规则与参数、输出、适用范围 | 与实测事实分开 |
| 事实快照 | 固定实体、几何、关系、证据及本体依赖 | 历史解释可复现，动态状态另固定游标 |

以上是逻辑设计，不是拟直接添加到旧 JSON 的字段清单，也不等同一张表。场景实例经候选、核对、采用与发布形成事实；部分内容未核实必须保留其状态。

以 PD-01 为例：L1 定义物理设备、位置、属性断言与观测；L2 定义配电柜、额定电压和电气端口；L3 记录某场景 PD-01 的类型、铭牌参数、所在空间、已核实连接及电流报告。不得在 L2 写入 PD-01，也不能从“配电柜”类别推导其实际参数。

## 8. 契约与依赖锁定草案

| 拟设计载体 | 职责 | 实现前必须明确 |
| --- | --- | --- |
| 本体模块包 | 定义与所属命名空间 | ID、字段、支持的语义子集、内容摘要 |
| 定义集合锁定清单 | 固定完整模块和规则依赖闭包 | 版本/摘要精确匹配、冲突检测、确定性解析 |
| 场景配置集 | 选择模块、约束、规则和参数要求 | 可选性、覆盖范围、适用条件及版本 |
| 来源映射包 | 原始分类/字段与目标定义的映射 | 精确源版本、映射强度、规则和未映射项 |
| 实例事实快照 | 锁定某个场景的实际描述 | 作用域、定义集合引用、成员及证据摘要 |
| 校验与迁移报告 | 解释合法性及变更影响 | 可定位诊断、覆盖/缺失、旧版解释保护 |

依赖全部精确锁定模块 ID、版本与摘要，不在固定发布中保存可变范围或 latest。编制期可提出版本范围，封存前解析成唯一闭包。缺失依赖、循环依赖、定义冲突、摘要不符或不支持的必需语义必须拒绝，不能退回“最接近版本”。

跨模块引用使用模块身份加本地 ID；未来是否采用全局 IRI 在契约设计中决定。相同标题不代表相同概念；本地 ID 相同但命名空间不同也不得自动合并。

严格离线消费携带解释必需的定义、约束、规则和固定映射依赖；大体量历史遥测不强制全部打包，但所声明的状态截面和证据能力必须真实可取得。定义集合被裁剪时仍保留传递依赖及明确的能力限制。

## 9. 版本、治理与授权

职责建议：产品语义维护者维护 L1，领域负责人维护 L2，场景工程师维护 L3；专业安全规则需具备相应依据与评审。人员可以兼任，记录和权限分开。

现有共享模板只读、Workspace 私有草稿与固定版本隔离继续有效。Workspace 扩展不能覆盖共享核心 ID；跨 Workspace 共享须另有显式发布及授权设计，不通过场景查询泄露私有定义、引用数量或业务实例。规则包不能代替服务端场景授权；商业订阅与配额继续由平台负责。

版本变更按实际语义影响评估：增加可选定义也可能改变推理结果，不能一律视为无影响。缩窄值域、增加必填、改变端点、修改身份或含义通常需要重点迁移评估。语义版本号只是提示，兼容性必须通过规则和实例影响报告说明。

生命周期：草稿 → 定义检查与依赖解析 → 语义评审 → 固定版本 → 场景选择 → 实例影响检查 → 新候选核对与发布。停用/弃用阻止何种新使用须明确，不能删除旧发布解释依赖。迁移保留未决项，不静默改写历史。

## 10. 态势地图、应用与智能体

同一实例身份衔接地图、人视图和计算视图。地图可组合固定空间事实、实时观测、派生结论及业务处置记录；颜色、图标和图层属于表现配置，不能反向成为本体事实。

查询应支持解释“是什么、在哪里、与谁关联、某时刻来源怎样报告、依据是什么”。返回固定发布/定义集合、空间参照及必要状态游标。未知、不支持、范围外、数据损坏和无权限继续分别表达。

未来动作契约可定义操作对象、输入、前提、权限要求、执行系统、幂等和结果回执。执行授权由服务端核实，动作调用不等于动作成功，结果需回执或后续观测确认。CoSpace 不因定义动作而成为机器人控制栈；通行、轨迹、接近和作业决策仍属于下游应用。

自然语言和模型可提出类型、匹配、查询或规则草稿，正式采用需可检查的结构化输入与来源。模型生成不得直接获得“已核实”标记。

## 11. 与当前工程衔接

基线以具体契约为准；旧 README 中“关系未实现”等早期描述不能代表当前完整状态。

| 当前能力 | 三层设计中的位置 | 后续缺口 |
| --- | --- | --- |
| `preview-ontology` 0.1/0.2，设备词表 0.3.0 | 既有版本化规则子集；词表内容主要为领域定义 | 单包引用、字符串属性，尚无模块闭包与通用数值单位 |
| Workspace 草稿、修订、固定版本、比较与使用查询 | 复用本体治理基础 | 新模块依赖、语义影响、跨模块诊断另行扩展 |
| 对象点锚、包含/连接关系、候选与固定发布 | L3 的既有受限实例表达 | 多类型、关系属性、多端连接、断言时态不能直接塞入旧协议 |
| IFC 类型提案 | 来源映射候选 | 不证明现场用途、属性值、几何对齐或连接成立 |
| 门状态观测内核与只读消费 | L3 动态观测的已有专用子集 | 通用指标、真实来源接入、单位和生产容量另行验证 |

复用 `packages/ontology` 承担定义、依赖和规则；`spatial` 承担实例/几何/时态事实；`construction` 产出候选；`data` 管资料与来源；`lifecycle` 管采用和发布；`views` 派生表达；`service` 组合授权查询。需要跨模块编排，不新增竞争的权威空间图。

新语义能力使用独立契约/profile 或经验证的适配器，保留旧类型及固定解释。旧 `room` 在现有设备词表中含设备间语义，不能直接当作新核心“任意房间”重解释。旧 contains/located_in 的单父/无环和 connected_to 的双向语义保持；供电等有向关系不得伪装成旧 connection。

## 12. 验收原则与待决项

总体验收由多个差异场景验证共享定义，不以一个样板项目通过替代体系成立。覆盖语义、来源、实例、几何、状态、授权、在线离线和升级边界，详见[实施规划](三层语义本体体系实施规划-v0.1.md)。

待决项：正式模块 ID 与命名空间、最小核心词典、继承/多类型支持子集、单位与时间编码、作用域与跨场景身份策略、关系端口契约、规则执行子集、依赖包预算、外部标准复用清单及其许可证、存储迁移与回滚。

上述事项有设计关口，不阻止先进行跨园区概念盘点。首轮先交付可审阅的词典、关系矩阵及正反例，再决定运行契约和代码，不先建设庞大编辑界面。
