# 智能体恢复状态机实现

日期：2026-10-27。J3独立Windows合成实验，代码位于experiments/scripts/recovery_state.py。依据[恢复日志协议](智能体恢复独占与提交日志协议-v0.1.md)。不接入平台API、R1默认入口或真实机器人。

J4首批补充：[显式文件会话适配与只读审计](智能体恢复与文件会话组合设计-v0.1.md)已接通并通过15项专项；仍使用测试时间锚，未改R1默认入口，没有并发/跨进程组合验收或生产维护权限。

## 实验版本与维护边界

RecoveryStore继承J2的消息留存、提交事务、状态规则与锁，但只在显式新目录初始化user_version=3的实验库。已有J2 user_version=2、v1门禁及J1控制库不自动升级。J2只增加可覆盖的版本/建表扩展点，原版本默认仍为2；不存在隐式ALTER或数据转换。

在原有messages/intents/receipts/states/control上增加recovery_runs和不可变recovery_plans。一个库最多有一个未完成恢复。恢复记录/计划受既有intent限额约束，不按年龄清理。全部恢复方法先取得J1 OS锁，再核对上下文、文件身份、存储代次和当前状态摘要。

## 调用与代次

| 方法 | 持久行为与使用条件 |
|---|---|
| begin_recovery(id) | 仅normal且有未决intent时接受；递增generation，写recovering与blocked恢复记录，同事务提交 |
| resume_recovery(id) | 仅继续同一个未完成恢复；再次递增generation、回到blocked，旧计划保留但失效 |
| plan_recovery(id) | 重放历史、对账未决、在内存暂演目标状态；保存不可变计划及planned阶段 |
| commit_recovery(plan) | 核对封存计划与当前全部比较条件；重新对账，将状态、全部receipt和恢复结果同事务提交 |
| recovery_result(id) | 诊断读取：未完成返回blocked；已完成返回原持久结果，不重新执行 |

begin/resume不原地刷新调用对象；调用后必须新建RecoveryStore。恢复完成时也推进一次generation，拒绝恢复期间打开的对象继续消费，包括恢复执行者。该完成代次是本批新增约束：生成receipt/result使用处理代次，control进入下一代次；它不参与状态摘要，不改变原已签期限。

计划绑定store/context/generation/recovery_id、期望修订号/前态摘要、完整未决集合摘要及排序动作列表、目标状态摘要。提交只接受本库封存的原计划；更改任一字段无法匹配封存摘要。即使封存计划未改，当前未决集合或状态变化也会在重新对账时拒绝。调用方JSON先复制为独立值，防止提交期间改变比较对象。

## 全历史重放与未决对账

从空状态开始，按本地不可变receipt的SQLite rowid提交顺序重放全部已完成意图。逐条定位消息原字节、核对摘要和身份、验签及委托限制，重新执行原状态规则，并对比结果、原因、前后修订号和状态摘要。最终重放摘要必须等于当前control和states。重放在内存数据库中执行，文件库不因规划而改变。

历史的签发时点可验证性与当前使用有效期分开：到期不会抹去历史撤回；重放不调用当前时间来重新授予能力。配置指纹固定，历史密钥失陷或无法验签时本批不做信任迁移，保持阻断。原消息缺失、被改、receipt链缺口、身份或状态不一致均不产生可提交计划。

对全部未决意图按intent_id排序，每项在重放后的状态上模拟apply、record_idempotent或record_rejection。允许记录确定性逻辑拒绝，例如恢复allowed但已有终止撤回，仍记rejected并保留撤回。**未决消息自身包含撤回，且无法应用时保守阻断**，不以rejected跳过可能的撤回。

本实现遇到不可解释项时抛出明确故障、保留blocked/planned，不生成含retain_blocked的可提交计划；Schema中的该动作仍为后续诊断表达保留。规划期间失败不会删除消息或修改当前空间状态。

首批重放有界：受JournalLimits约束，未决项最多200。恢复时需对历史进行多次验签和暂演，持锁时间可能明显长于普通查询，本批不承诺大日志性能。normal接收最多留下一个未决项；多项循环的回滚测试使用显式合成注入，不能据此宣称正常入口支持批量导入。

## 原子结束与中断

提交先重新生成当前计划并逐字段比较，再在同一真实事务中应用各项状态及receipt，核对目标摘要与无剩余未决；最后写mode=normal、完成结果并推进完成代次。中途任一项或完成提交前失败，整批回滚，recovering保留。调用方不能单独将mode改normal或清除intent。

| 故障点 | 再打开后的结果 |
|---|---|
| begin提交前 | 原状态保持，未决意图继续阻断 |
| begin/plan提交后中断 | 持久recovering；可显式resume同ID，但不能自动继续旧计划 |
| 逐项写入后、完成提交前中断 | 所有恢复写入回滚，无部分receipt或部分解除 |
| 完成提交后、响应前中断 | 按同recovery_id读取reconciled；不允许重复应用或resume |

SQL/IO故障锁存当前对象的storage_fault；新对象仍由持久mode/未决集合/代次判断。恢复完成仅表示日志对账完成，新对象依然逐次执行时间与撤回门禁，可能返回revoked、expired或grant_missing。新会话和可信时间锚的正式装配留到J4/设备验证；本批没有生成可信时间。
