# 证据内容核对与接入 v0.1

日期：2026-11-17。SG3、SG4、SG5 共用的字节完整性前置能力。此前复核记录和观测报告可声明证据摘要，但摘要所指文件未必存在或仍保持原内容。本轮增加实际文件核对，并接入三个批次已有流程；不是现场复核、来源认证、正式采用或发布审批。

## 1. 文件与回执

可信调用方配置一个本地证据根目录，文件按 `<SHA-256>.bin` 存放。这里是受控目录约定，不是上传接口；不得把浏览器/厂家传来的路径作为根目录。原始文件不重命名或覆盖，可将明确获准使用的副本放入该目录。不同租户应使用各自授权隔离的根目录，不能把全局摘要可猜测当作访问授权。根目录、文件内容和回执仅留受控运行/证据目录，不进入 Git。

`packages.data.evidence_content.check_evidence_content(root, references, document_sha256=...)` 接收严格的 `{id, sha256}` 列表；不接受路径、URL、额外字段、重复 id 或空引用。一个文件可被不同证据 id 引用，按不同摘要各读取一次；不同 id 并不证明证据相互独立。

最多 2,048 个引用，单文件 1–16 MiB，不同文件总计最多 64 MiB。先检查全部文件类型与大小，再以 1 MiB 块读取、计算 SHA-256；不解压、不执行、不解析媒体。拒绝符号链接、junction、非普通文件、缺件、摘要不符和读取期间可检测的文件替换/变化。Windows 路径与句柄的 ctime 表达不同，因此跨 API 比较设备/inode/大小/mtime，同 API 内额外比较 ctime。没有锁定整个证据目录，不能承诺对抗恶意并发替换或提供数据库式全局快照；文件应在受控只读阶段使用。

返回 `cospace.evidence-content-check/0.1`：固定 `document_sha256`、每个引用 id/摘要/字节数、不同文件数、总字节数及 `receipt_sha256`。不包含本地路径。`content_integrity_checked=true` 仅表示本次实际读取的文件符合摘要；`meaning_verified`、`source_identity_verified`、`real_release_ready` 均为 false。

回执摘要不是签名，也不是认证令牌；不能接受客户端自造回执作为权限或事实依据。document_sha256 必须由调用方对已核对的输入计算或从可信发布上下文取得。仅给出任意摘要并不证明输入来源。文件后续可能被移除，回执不代表永久留存；再次执行需重新读取，不能复用旧回执绕过缺件检查。

## 2. SG3：配准复核与空间标注

`ifc_reviewed_alignment` 增加可选 `--evidence-root`，核对单位依据和全部控制点依据；回执绑定复核记录的规范内容摘要，该记录本身绑定工作表及固定 IFC/点云。既有逐点原坐标、索引、独立检查点和误差检查继续执行。

`ifc_spatial_annotation --worksheet ...` 同样增加可选 `--evidence-root`，核对工作表登记的所有证据（含尚未引用者），回执绑定完整工作表摘要。空工作表无证据时不支持该选项；创建空表不能带此选项。原来源、区域和端点校验仍执行。

不带选项保留旧的“仅声明证据摘要”行为，不输出核对回执。带选项失败则不生成输出文件。两种路径都不会认证文件内容含义、人工复核者身份或现场一致性：原 `evidence_content_verified`、`alignment_verified` 等标志保持 false，新增 `evidence_receipt.content_integrity_checked` 单独表示字节核对。以此避免把“文件存在且正确”混成“点位和连接已经确认”。

## 3. SG4：固定资料包的原始来源核对

Python `read_design_package` / `inspect_design_package` 增加可选 evidence_root。先按可信 expected_sha256 / expected_source 完成资料包、结构和全部网格组件检查，再从证据目录核对固定原 IFC 的摘要与字节数。回执绑定资料包的原始字节 SHA-256，read 方法返回 evidence_receipt；summary.original_ifc_content_verified 才会变为 true。

这不等于重跑 IFC 解析或证明结构/网格派生过程正确。original_mesh_content_verified、alignment_verified、ontology_bound、real_release_ready 不变；包内仍是 ifc_design_candidate / unverified。资料包格式、下载接口、Node 默认消费行为不变。原 IFC 大于本轮 16 MiB 文件预算时明确拒绝，不截取；没有扩大协议宣称的全部来源支持范围。

## 4. SG5：整批证据检查后追加

内部方法 `packages.service.observation_admission.append_with_evidence(journal, scope, reports, authenticated_producer=..., evidence_root=...)` 为未来厂家网关提供可调用的接入步骤：

1. 校验作用域、1–128 条报告及来源字段与调用方认证结果一致；对象必须在该作用域登记。
2. 核对整批报告引用的所有不同证据摘要。回执绑定规范化的 scope + reports（含默认字段），不同租户、目录或报告不能共用同一上下文摘要。
3. 调用既有 append_batch，在同一数据库事务内再次校验来源登记、对象、幂等键、纠正链、容量及时间，全部追加或全部回滚。

证据缺件/改写时不会追加任何报告；数据库阶段失败也不部分提交。重试重新校验证据，即使原报告已存在。回执随结果返回给可信调用方，当前不持久化回执、不修改原观测日志格式，也不把状态读取中的 evidence_content_verified 改为 true。

文件读取发生在数据库事务前；它证明检查时刻的字节，不保证提交后的永久可用性。证据目录只读保留、回执持久化与留存/恢复、厂家身份/签名、时钟质量和证据含义核验仍需独立建设。调用方须在进入此方法前完成认证及场景授权；authenticated_producer 不得从同一报文复制充当认证结果。本轮没有开放 HTTP 写入口、创建厂家凭证或商业限额，没有自动注册对象，也未改变旧的内部 append 接口。

## 5. 三批验收边界

SG3 现场单位、对应点、区域/连接和资产身份仍待真实依据；SG4 已核实事实快照与正式授权发布仍未完成；SG5 真实厂家/时钟/证据含义、真实上报及局部更新仍未验收。用户现有目录已全部检查的结论不变，不反复索取额外文件，也不把设计文件或软件测试材料当作现场证明。
