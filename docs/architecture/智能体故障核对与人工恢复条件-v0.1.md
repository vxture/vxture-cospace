# 智能体故障核对与人工恢复条件

日期：2026-10-27。范围：R2b第三批合成只读工具与恢复条件设计。依据[故障门禁补充](智能体密钥委托与故障门禁补充-v0.1.md)。只读核对已实现；解除、修复和信任迁移尚未实现。

## 核对入口与职责

experiments/scripts/validity_audit.py独立打开现有validity-test.sqlite3，使用mode=ro和query_only，不调用ValidityStore构造器，不初始化、补表或写库，不删除pending条目。报告输出到stdout，调用方可以另存到独立证据目录。原R1安装审计保持独立，不能用包安装正常证明有效性门禁可用。

数据库在单个读取事务中观察配置摘要及当前保留证明的原字节摘要；pending文件在事务之外观察。两者不是原子快照，报告不证明当前没有写入者，也不证明核对结束后的门禁状态。报告不读取文件年龄、不检测进程是否存活、不执行签名或时间有效性验证。

默认最多100条状态、100个pending条目，limit可设1至200。单个标记最多1024字节、单证明受现有MAX_TOKEN限制、证明总字节最多4MiB；另设SQLite长度及执行步数预算。超限、坏库、危险路径、未知文件类型或读取失败均报告不完整，不给出部分清理结论。文件系统并发替换防护仅沿用本地受信工作区的safe_path检查，不是恶意用户沙箱。

## 报告语义

| 字段或分类 | 解释 |
|---|---|
| complete | 本次有界读取完成；不是全部状态正确或运行获准 |
| database_observed | 读取到了预期表与摘要字段；不是完整数据库审计 |
| needs_attention | 本次观察到pending条目或读取问题 |
| retained_digest_match | 标记的类型及摘要匹配当前保留证明原字节；尚未验签 |
| not_in_retained_snapshot | 当前保留证明中没有匹配；不能判断从未提交 |
| database_unknown | 无法建立数据库观察，仍保留文件侧条目 |
| unresolved_entry | 标记不可读、超限、名字/类型/结构异常 |

报告固定proofs_verified=false、cleanup_authorized=false、recovery_authorized=false、authorized=false、robot_ready=false。不输出原始证明正文；匹配结果只给状态身份及摘要，降低诊断泄露面。

未匹配有多种原因：写入仍在途、事务未提交、曾提交的旧状态已被更新替换、内容损坏或数据库读取不完整。现有states只保留当前证明，pending只保存摘要，没有完整提交历史或写入者身份。故而“摘要相同”“文件较旧”“数据库中没找到”都不足以解除门禁。

## 人工恢复的必要条件（待实现）

1. 建立维护独占窗口：停止或隔离所有写入、激活及消费会话，并取得可核验的所有权证据。当前ValidityStore没有覆盖全体参与者的恢复互斥协议，不能靠“等待若干秒”替代。
2. 保存故障现场：原库、相关SQLite日志、pending原字节和摘要、受控配置版本及诊断结果。按一致性备份协议取证，不能在活跃事务中简单拷贝主库；不保存私钥。
3. 从外部受信来源补齐消息：按原字节摘要定位每个未确认消息，验证根委托、角色、部署、场景、受众、版本、时效和完整binding。未知条目与消息缺失保持未解决。
4. 对账状态与撤回：区分未提交、已提交、已被后续状态替代或无法判断。最新受信状态不得降低epoch/sequence，累积终止撤回不得丢失。新grant必须重新绑定状态及策略，不能沿用失配的旧grant。
5. 对账全部成功后才提交恢复决定：以独占令牌、故障集合摘要和预期状态版本作为比较条件，记录持久恢复凭据；中断后可重复核对，不能留下“标记删除了、决定却没提交”的窗口。具体跨文件/数据库提交协议仍待设计。
6. 重新取得时间锚并打开新会话：恢复操作不延长已签状态的离线时限；原对象的storage_fault不原地复位。新会话仍逐次检查门禁，失败保持拒绝。

以上是必要设计条件，不是当前可执行操作手册。本批不提供删除命令、恢复API、管理按钮或自动重试。数据库缺失、坏库、信任指纹变化、无法确认的历史撤回分别走专门的恢复/迁移协议，不能删除旧库并bootstrap规避。
